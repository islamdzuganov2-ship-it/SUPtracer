# TaskTreker — портфель проектов

Одна панель по всем вашим проектам сразу, в двух вкладках:

- **Дашборд** — диаграммы и цифры: готовность по пяти измерениям, вложено против оставшегося,
  цена пункта готовности, затраченное время, количество и качество ТЗ, качество проработки,
  расход по месяцам. Плюс десять портфельных сигналов с уровнем «норма / следить / действовать».
- **Проекты** — полная информация: что сделано, бэклог с размерами и оценкой затрат,
  безопасность, архитектура, мощности, LLM, цели, оценка и конкуренты.

Работает локально, без сервера, без сети и без зависимостей — только Python из стандартной
библиотеки. Дашборд открывается двойным кликом по `dashboard.html`.

Чем отличается от счётчиков расхода вроде `ccusage`: расход токенов здесь — одна колонка
из десяти, а не вся панель. Чем отличается от Jira: половина данных собирается сама, с диска
и из журналов, а не вбивается руками.

Плюс к панели — **память портфеля**: знание о проектах хранится в системе, а не в окне
контекста ассистента, заметки Markdown и хранилище Obsidian разбираются и раскладываются
по проектам сами, а на дашборде растёт дерево работ — из какого запроса что выросло.

## Быстрый старт

```bash
git clone https://github.com/islamdzuganov2-ship-it/SUPtracer.git && cd SUPtracer
```

```bash
py tools/pm.py init
```

Разложит примеры в рабочие файлы. Впишите свои проекты в `data/projects.json` — главное поле
`path`, по нему собирается и код, и расход токенов. Затем:

```bash
py tools/pm.py refresh
```

Соберёт всё: расход токенов из журналов сессий → технический срез репозиториев → оценку
оставшихся задач → дашборд → снимок для истории. Открыть: `py tools/pm.py open`.

## Комментарии превращаются в бэклог

Мысль по проекту записывается одной командой и при следующем разборе становится задачей:

```bash
py tools/pm.py comment мой-проект "Перед релизом проверить, что дебаг-флаг выключен" --kind техдолг
```

Виды: `техдолг`, `идея`, `баг`, `вопрос`. Разбирает их ассистент по регламенту из
[CLAUDE.md](CLAUDE.md): определяет размер, переносит в бэклог нужного проекта и помечает
комментарий обработанным с указанием, куда именно он ушёл. Ничего не удаляется — разобранный
комментарий остаётся следом решения.

## Память вместо контекста

Обычно ассистент держит всё, что знает о проектах, в своём окне контекста: каждая сессия
перечитывает файлы целиком, платит за запись кеша и за чтение кеша, а между сессиями знание
теряется. Здесь знание лежит в системе — записями в `data/memory/*.md`, — а в контекст
попадает только указатель:

```bash
py tools/pm.py context
```

Брифинг: что требует решения, состояние проектов, верхушка бэклога и список записей памяти —
заголовки и идентификаторы, без содержимого. Внизу честно написано, во что брифинг обошёлся
и во что обошлось бы чтение `data/` целиком; на портфеле из нескольких проектов разница
обычно в десять и более раз. Нужное берётся точечно:

```bash
py tools/pm.py recall <id или слова>
```

Записать новое знание:

```bash
py tools/pm.py remember мой-проект "Кеш вынесли на диск" --text "Сетевое хранилище отвергли: лишняя движущаяся часть" --kind решение
```

Виды записей — `запрос`, `решение`, `требование`, `риск`, `итог`, `факт`, `источник`,
`заметка`. Устаревшее не удаляется, а помечается `forget`: история решений нужна так же,
как сами решения.

### Во всех проектах сразу

```bash
py tools/pm.py connect
```

Подключает систему к Claude Code на уровне пользователя. **Хук начала сессии** даёт
брифинг по проекту того каталога, где открыта сессия, — в бюджете 1200 токенов; вне
портфеля он молчит одной строкой. **MCP-сервер** `tasktreker` даёт ассистенту
инструменты `tt_context`, `tt_recall`, `tt_remember`, `tt_status`, `tt_tree` и другие —
в любом проекте, без путей к скриптам. Сервер написан на стандартной библиотеке и
понимает обе эпохи протокола MCP: современную (версия в каждом запросе) и наследную
(рукопожатие `initialize`). Бэклог через него меняется только принятием предложений.

Настройки пользователя вливаются, а не перезаписываются; снять всё — `pm.py disconnect`.

## Заметки Markdown и Obsidian

Разбор входящих живёт в системе, а не в рассуждении ассистента: правила записаны один раз
и применяются одинаково.

```bash
py tools/pm.py ingest ~/Заметки/планы.md
```

Файл режется на разделы, каждый получает вид (запрос, решение, требование, риск, итог),
проект определяется по фронтматтеру, тегам, ссылкам и словарю проекта, а задачи-чекбоксы
уходят предложениями во входящие — `py tools/pm.py inbox`. В бэклог они попадают только
по команде `apply`: бэклог считает деньги, и решение «это задача» принимает человек.

Хранилище Obsidian подключается целиком, в обе стороны:

```bash
py tools/pm.py vault init "C:/Users/вы/Документы/Мой Vault"
```

```bash
py tools/pm.py vault sync
```

- **Внутрь** — заметки разбираются и раскладываются по проектам; неизменившиеся файлы
  повторно не читаются.
- **Наружу** — в хранилище появляются страница портфеля, страница на каждый проект,
  дерево работ и записи памяти: обычные заметки с викиссылками, так что граф Obsidian
  показывает ту же структуру, что и дашборд.
- **Галочки работают.** Отметили задачу сделанной в Obsidian — при следующем `pull`
  статус меняется и в системе.

Формат записей памяти — Markdown с фронтматтером, то есть родной формат Obsidian:
интеграция не требует конвертации.

## Дерево роста на дашборде

Отдельный раздел дашборда — дерево работ: корневой запрос слева, из него решения,
требования и риски, из него же задачи, в которые он превратился. Отдельно видно
фундамент (сделанное, на что всё опирается) и почки (предложения, ещё не принятые).

Толщина ветви — вес поддерева в токенах: во что эта ветка обошлась или обойдётся.
Ползунок «рост» отсекает узлы по дате появления, кнопка «рост» проигрывает историю
по месяцам — дерево разрастается на глазах, а не показывается сразу целиком. Ветви
сворачиваются кликом, есть поиск, масштаб колесом и перетаскивание.

Связь «задача выросла из запроса» хранится в поле `root` задачи бэклога — его проставляет
разбор заметок и команда `apply`. Задачи без связи видны отдельной ветвью: несвязанная
работа сама по себе наблюдение.

## Кнопка «Обновить данные»

Дашборд открывается двойным кликом и работает без сервера — но тогда кнопка обновления
может только показать команду: страница на `file://` не имеет права ничего запускать.
Чтобы кнопка работала по-настоящему:

```bash
py tools/pm.py serve
```

Локальный сервер на `127.0.0.1`, отдаёт ровно один файл и принимает одно действие —
пересобрать данные (быстро, полностью или с обменом с Obsidian). Наружу машины не виден.


## Что измеряется само

| Метрика | Откуда берётся |
| --- | --- |
| **Затраты** — токены и деньги | журналы сессий, дедупликация по `requestId` |
| **Время** — активная работа | отметки времени в журналах: сумма промежутков между ответами, паузы длиннее 15 минут отброшены как перерыв |
| **Количество ТЗ** | коды требований в документах, схемы нумерации, объём и структура |
| **Качество ТЗ** | трассируемость (какая доля кодов требований встречается в коде), дисциплина документирования, плотность открытых вопросов |
| **Качество проработки** | тесты, версионирование, гигиена поставки, чистота кода, подозрение на секреты |
| **Цена пункта готовности** | потраченные деньги, делённые на процент функциональной готовности |

Индексы качества — взвешенная сумма нормированных компонент. Каждая цифра раскладывается
до компоненты с её весом и сырым значением, поэтому её можно оспорить по существу.
Пороги нормировки — в [`tools/quality.py`](tools/quality.py).

## Как считаются затраты

**Факт.** Журналы сессий Claude Code (`~/.claude/projects/*/*.jsonl`) содержат `usage` каждого
ответа. Сборщик дедуплицирует по `requestId` — **каждый ответ пишется в журнал дважды, и без
дедупликации расход завышается ровно вдвое**. Проект определяется по `cwd`, рабочие деревья
(worktrees) сворачиваются в родительский проект.

Это решает известную проблему: Claude Code не размечает запросы метаданными проекта, поэтому
привязать расход к проекту напрямую нельзя.

**Деньги** — эквивалент по прайсу Anthropic API, а не счёт подписки. Считаются раздельно вход,
выход, запись кеша (1.25× от входа при TTL 5 минут, 2× при часе) и чтение кеша (0.1×). Прайс
в [`tools/pricing.py`](tools/pricing.py).

**Прогноз.** Размер задачи (S/M/L/XL) переводится в коммиты, коммит — в токены по
**фактическому расходу в этом же проекте**. Где своей истории мало, берётся медиана портфеля.
Это стоимость работы ассистента, а не трудозатраты человека.

## Ветки

Три ветки, движение строго в одну сторону:

```
разработка  →  тестирование  →  main
```

| Ветка | Что это | Что в неё попадает |
| --- | --- | --- |
| `разработка` | рабочая, здесь живёт вся текущая работа | любые правки: данные, инструменты, документация |
| `тестирование` | проверочная | только то, что прошло `py tools/pm.py check` |
| `main` | стабильное состояние | только то, что отработало в тестировании |

Прямые коммиты в `тестирование` и `main` не делаются — туда сливают из предыдущей ветки.

**Гейт между ветками:**

```bash
py tools/pm.py check
```

Четырнадцать проверок: целостность данных (обязательные поля, диапазоны готовности, обоснование каждой
цифры, уникальность задач бэклога), согласованность ручного слоя с автоматическим (весь расход
разнесён по проектам, оценка покрывает бэклог, разобранные комментарии указывают куда
перенесены), целостность памяти (у записей есть вид, проект и тело, родитель не потерян,
индекс сходится с файлами), принятые предложения дошли до бэклога, отсутствие ключей
в данных и в памяти и то, что дашборд собирается со всеми проектами.
Код возврата 1 — сливать нельзя.

```bash
git checkout тестирование && git merge --no-ff разработка && py tools/pm.py check
```

## Автоматизация

Два уровня: факты обновляются без участия модели, суждения — с ним.

| Что | Когда | Стоит токенов |
| --- | --- | --- |
| **Факты**: токены, репозитории, оценки, дашборд, снимок | ежедневно, планировщик ОС → [`ops/refresh.cmd`](ops/refresh.cmd) | нет |
| **Суждения**: разбор комментариев, сверка записанного с фактами, отчёт | еженедельно, запланированная задача ассистента | да |

Ежедневная задача трогает только генерируемые файлы. Готовность, бэклог, оценка и
безопасность меняются либо еженедельным разбором, либо прямой командой.

Регистрация ежедневной задачи в Windows:

```bash
schtasks /Create /TN "TaskTreker\Обновление портфеля" /TR "%CD%\ops\refresh.cmd" /SC DAILY /ST 09:00 /RL LIMITED
```

## Тесты и качество

```bash
py -m unittest discover -s tests
```

Полторы сотни тестов на стандартной библиотеке — разбор заметок, память, приём, входящие,
дерево, брифинг, хук, MCP-сервер по обеим эпохам протокола, обмен с Obsidian, сервер
дашборда, вычистка ключей и прогон всех команд на пустых данных. Каждый тест работает
в своём временном каталоге данных и рабочий портфель не трогает. Гейт `pm.py check`
запускает их сам.

Точность раскладки заметок по проектам измеряется на размеченном наборе:

```bash
py tools/routing_eval.py tests/fixtures/routing
```

Требования к памяти, приёму, Obsidian, дереву и подключению ассистента — в
[docs/ТЗ_01_Память_Obsidian_Дерево.md](docs/ТЗ_01_Память_Obsidian_Дерево.md): коды
требований стоят в коде рядом с реализацией, поэтому система меряет трассируемость
своего ТЗ так же, как у остальных проектов портфеля.

## Требования

Python 3.10+ (проверено на 3.14), только стандартная библиотека. Git — для среза репозиториев.
