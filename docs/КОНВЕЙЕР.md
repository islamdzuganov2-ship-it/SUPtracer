# Конвейер задач: от идеи до main

Доска «Доски задач» — это конвейер из семи этапов. У каждого этапа есть роли-агенты,
DoR (условия, чтобы роли взяли задачу) и DoD (условия, чтобы сдать этап). Всё это
задано данными в `tools/pipeline.py`: по ним проверяет сервер, из них собраны скиллы
ролей (`skills/tt-*`), их показывает доска (кнопка «DoR / DoD» в заголовке колонки).

| Этап | Роли | Ворота |
|---|---|---|
| Идея | Product Owner | — |
| Анализ | Системный аналитик, Solution-архитектор; UX/UI-дизайнер и маркетолог — если их решил подключить PO | ИИ-тимлид: «анализ → разработка» |
| Разработка | Разработчик | — |
| Ревью | Ревьюер | — |
| Деплой в тест | DevOps-инженер | — |
| Тестирование | QA-инженер | ИИ-тимлид: «тест → main» |
| Деплой в main | DevOps-инженер | «Да» владельца |

Порядок «сначала деплой в тест, потом тестирование» — решение владельца 31.10.2026: QA проверяет
развёрнутую тестовую ветку (паспорт QA, поле `test_env`: ветка, рабочая копия, последний прогон
CI), а в main уходит только то, что прошло тестирование без открытых дефектов.

«Отменено» — восьмая колонка. Задачи вне конвейера (заведённые до него или формой
«＋ Новая задача») стоят в колонке по своему статусу: готовые — в «Деплой в main»,
непроработанные — в «Идея», в работе — в «Разработка», на проверке — в «Ревью».

## Как задача попадает в конвейер

- Из терминала Claude Code или Codex: ассистент вызывает `tt_work op=idea project=… title=… text=… source=claude|codex`.
- С доски: кнопка «💡 Идея».
- Из командной строки: `py tools/pm.py idea <проект> "название" --text "что и зачем"`.

Идея становится задачей в «Идея» с исходным запросом в памяти проекта. Сразу создаётся
рабочая копия задачи `<проект>.worktrees/task-<id>` с веткой `task/<id>`: в ней роли
пишут артефакты (`docs/tasks/<id>/`) и код — всё едет одной веткой до main.

## Как работает оркестрация

Тимлид-оркестратор — сервер (`tools/orchestra.py`):

1. Проверяет DoR этапа. Не выполнен — задача ждёт с причиной на карточке, событие в журнале тимлида.
2. Ставит запуски ролям этапа. Сервер досок открывает их сессии сам, если включено «Конвейер:
   открывать сессии ролей автоматически». Сессия — окно Claude Code или Codex на модели роли (не ниже
   её класса: PO и архитектор — старший), со скиллом роли и правом правки файлов в рабочей копии
   (Claude — `acceptEdits`, Codex — `workspace-write`). Команды подтверждает владелец.
3. Роль сдаёт работу `op=handoff` со списком пунктов DoD. Это и есть уведомление тимлиду: событие
   уходит в журнал. Сервер проверяет пункты:
   - артефакт закоммичен в ветку задачи, есть все разделы-заголовки, нужный размер;
   - доказательство не короче 20 символов;
   - машинные пункты: ссылки на источники, диаграммы, таблицы, открытые дефекты, коммиты,
     слияние без конфликтов, секреты, тесты.

   Не выполнен хоть один пункт — передача не принимается, запуск остаётся у роли со списком `failed`.
   «Неприменимо» допустимо только там, где это разрешено, и с причиной.
4. Тяжёлые пункты — прогоны CI, слияние в базовую ветку на ревью, деплой в тестовую
   ветку и в main — выполняются фоновым заданием (журнал `ops/logs/pipeline.log`). Провал возвращает
   задачу той же роли с замечаниями. После трёх провалов подряд — проблема уходит Решале.
5. Все роли этапа сдали работу → ворота, если есть → этап сдан → DoR следующего этапа.

Очередь сервера досок (решение владельца 31.10.2026 по разбору недели):

- **Анализ по порядку.** Архитектор и дизайнер ставятся только после сдачи системного аналитика —
  они читают готовое ТЗ, а не пишут контракты параллельно. Маркетолог от ТЗ не зависит.
- **Лимит незавершённого.** В анализе проекта — не больше `wip_analysis` задач (по умолчанию 6).
  Пока лимит занят, PO новые идеи не разбирает: сначала доводятся начатые.
- **Группы контрактов.** PO в `handoff` указывает `contract_group`, если задача делит API или модель
  данных с другими. Анализ задач одной группы идёт по очереди: следующий аналитик читает уже
  принятый контракт.
- **Порядок открытия:** Решала первым (и с одним местом сверх общего лимита), затем этапы ближе
  к main, затем приоритет и возраст запуска.
- **Лимит на каждый ИИ:** `sessions_per_ai` (по умолчанию по 2) — внутри общего `max_sessions`.
  Запуски ИИ, упёршегося в свой лимит, не задерживают запуски другого.

Все три числа меняет владелец на доске (⚙ Исполнение и ревью); через MCP они не меняются.

## Сверка анализа сервером и ворота

Противоречия контрактов раньше ловил тимлид через полный цикл. Теперь при сдаче аналитика (`sa-trace`)
и архитектора (`arch-trace`) сервер сверяет коды: FR/NFR/SR/UC/US определяются в SRS, BR — в BRD,
API — в `api.md` (без него — в SRS), ADR — в файлах `adr/`, TC — у QA (на анализе не проверяются).
Ссылка на неопределённый код или требование SRS вне RTM — передача не принимается. У SRS без кодов
требований передача тоже не принимается.

Тимлид получает в паспорте `digest`: сверку кодов, проваленные пункты DoD, возвраты, дефекты, CI —
и читает документы только там, где сводка показывает проблему. Ворота **простых** задач (класс 1,
без возвратов и открытых дефектов) закрывает сервер: анализ — при чистой сверке, релиз — при подписи
QA и зелёном CI на тестовой ветке. «Да» владельца на main сервер не заменяет.

## Экономия токенов

Мерило — количество токенов, а не деньги. Замер 92 сессий ролей Claude (300 млн токенов): старт —
43–46 тыс. токенов до первого действия, 94% токенов — чтение кеша, то есть контекст, заново
прочитанный в каждом ходе. Значит, каждый токен стартового контекста оплачивается столько раз,
сколько ходов в сессии (15–44). Поэтому:

- **Лёгкий старт сессии роли (Л1).** Сервер открывает сессию роли без плагинов, чужих MCP-серверов,
  пользовательских скиллов и хуков: `--strict-mcp-config` с одним сервером TaskTreker в режиме роли
  (в списке только `tt_work` и `tt_recall` с короткими описаниями), `--setting-sources project,local`,
  `--tools Bash,Read,Edit,Write,Glob,Grep` (веб-поиск — только PO, маркетологу и Решале при исследовании),
  скилл роли — в системном промпте (`--append-system-prompt-file`), машинные разделы промпта — в первое
  сообщение (`--exclude-dynamic-system-prompt-sections`). Правила автоматического режима берутся из
  пользовательских настроек. Замер на EGE: старт 54,8 тыс. → 14,7 тыс. токенов; на тех же 92 сессиях это
  ~79 млн токенов из 300 (26%). Codex получает режим роли MCP через `-c`. Отключить — `TASKTREKER_LEAN=0`.
- **Указатель документов (Л2).** Паспорт несёт не текст, а указатель: у артефакта в `upstream` и у
  крупного документа проекта в `project_docs` — вес в токенах и строки «номер · заголовок · вес ·
  строки · коды требований» (код — в разделе, где он впервые назван). Раздел — `tt_work op=doc ref=…
  path=… section=<номер или часть заголовка>` или `code=<FR-3>`, либо `Read` с offset/limit по строкам.
  Без `section` — указатель целиком. Коды бывают простые (`FR-3`, `FR-2.1`) и составные
  (`FR-POL-04`, `NFR-PERF-01`): указатель сворачивает подряд идущие в диапазон (`FR-ACC-01–03`).
- **ТЗ как данные: `docs/tasks/<id>/INDEX.md` (TT-92).** После принятой сдачи этапа идеи или анализа
  сервер собирает из закоммиченных артефактов указатель задачи и коммитит его в ветку отдельным
  коммитом: документы с разделами, весом и строками и реестр требований — код, суть одной строкой,
  документ, раздел и строка определения. Его читает любой агент — Claude, Codex, человек — вместо
  документов целиком. Есть `INDEX.md` — паспорт даёт путь (`task_index`) и вес артефактов, а
  построчных указателей каждого документа не дублирует. `op=doc code=<FR-3>` без `path` находит
  документ-источник кода сам. Замер на EGE-09: документы 23,4 тыс. токенов → указатель 3,1 тыс.
- **Полное чтение — по обоснованию, а не запретом (Л3, TT-96).** Хук сессии роли (`tools/read_guard.py`)
  и сервер работают по одной политике — `pipeline.read_policy` (роль × класс сложности задачи):
  - свой артефакт роли и **вход её этапа** читаются целиком без вопросов: аналитику — BRD, архитектору
    и QA — SRS, дизайнеру и маркетологу — BRD (`PRIMARY_INPUTS`);
  - документ до **порога класса сложности** (3, 5 или 8 тыс. токенов) — тоже целиком: раздел ненамного меньше;
  - крупнее — сначала указатель документа. Если задача действительно требует его целиком (сквозная сверка,
    согласованность всех разделов), роль пишет зачем: `tt_work op=doc ref=… run=… path=… full=true why=…`.
    Сервер отдаёт текст, пишет причину и вес в журнал тимлида (`read_full`) и считает **бюджет
    обоснованных чтений** запуска: 20, 50 или 120 тыс. токенов по классу. Бюджет исчерпан — разделы
    или эскалация;
  - повторное полное чтение неизменившегося файла от 8 КБ — отказ: его текст уже в контексте.
  Фрагменты по offset/limit не ограничены, сжатие контекста сбрасывает учёт. У Codex хука нет — то же
  правило в задании роли и тот же `op=doc full=true`.
- **Счёт токенов** (`pipeline.tokens`) откалиброван по точному счёту Claude (разница входа с документом
  в системном промпте и без): ASCII ~2,55 символа на токен, кириллица ~2,2; ошибка на BRD, SRS,
  регламенте и Python-модуле — в пределах ±9%.
- **Эстафета сессий (TT-91).** Каждый ход перечитывает весь контекст, поэтому длинная сессия дорожает
  квадратично. Потолок контекста роли — `context_ceiling` (по умолчанию 90 тыс. токенов, `op=settings`,
  0 — выключено). Хук сессии Claude после очередного инструмента смотрит контекст последнего хода и
  один раз (и ещё раз на 130%) напоминает: довести шаг, закоммитить и `tt_work op=pause
  reason=context checkpoint=…`. Сервер сразу открывает **свежую** сессию той же роли с точкой
  остановки (не `--resume`). Сессию, закончившуюся выше потолка без сдачи, сервер передаёт по
  эстафете сам, собрав точку остановки из последних реплик. Эстафет на запуск — не больше 4, дальше
  проблема уходит Решале. У Codex хука нет: правило — в задании роли, эстафету по журналу делает сервер.
  `pm.py tokens` суммирует все сессии запуска и показывает число эстафет.
- **Модель по сложности.** PO, архитектор, тимлид и Решала на простых и средних задачах — средний
  класс (Claude Sonnet, у Codex — Sol), старший класс и `xhigh` — только сложным. Таблица — `ROUTING`
  в `tools/pipeline.py`, она же в скиллах.
- **Исследование рынка — только продуктовым задачам.** PO решает `needs.research`; техническая задача
  (`research=false`) идёт без веб-поиска, с коротким BRD без разделов о рынке, `po-market` —
  «неприменимо». По умолчанию задача продуктовая.
- **Дизайнер — только при изменении интерфейса** (`needs.design`); скриншоты — не больше трёх за
  запуск, уменьшенные.
- **Сторож бюджета (Л4).** У запуска роли — ориентир `route.budget_tokens` (класс модели × усилия:
  1, 2,5 и 5 млн токенов). Сервер раз в 5 минут считает по журналу сессии все обработанные токены
  (вход, запись и чтение кеша, выход); на 150% — отметка в журнале тимлида, колокольчик и напоминание
  сессии при следующем продолжении: довести до handoff или эскалировать. У Claude то же видно и **внутри
  сессии**: хук после инструмента считает обработанные токены по журналу (с места прошлого подсчёта) и на
  100% и 150% ориентира напоминает сузить работу или довести этап до handoff.
- **Отчёт `pm.py tokens [проект] [--role R] [--since дата] [--json]`.** Среднее на запуск по ролям и ИИ:
  старт, пик контекста, ходы, чтение кеша, выход, всего, повторные чтения, сбережённое сторожем —
  отдельно для обычного и лёгкого старта, чтобы разница была видна в цифрах.
- **Раздел дашборда «Токены ролей» (TT-97, `tools/tokview.py` + `tokview.js`).** Считается при сборке
  из журналов сессий и workflow, без ИИ и без отдельного файла данных:
  - главная мера — **токены на принятую сдачу этапа** по ролям и неделям: все токены роли (с возвращёнными
    и упавшими запусками), делённые на сдачи, принятые по DoD. Если работа дешевеет, ячейки светлеют;
  - **контекст по ходам** недавнего запуска: потолок эстафеты, начала новых сессий, полные чтения;
    площадь под кривой — чтение кеша;
  - **было и стало** по оптимизациям (лёгкий старт, `INDEX.md` в паспорте) — медианы по ролям;
  - **роль × этап** — медиана токенов на запуск, и запуски вдвое дороже медианы своей роли — кандидаты на разбор.

Назад задачу возвращают `op=return`:
- ревьюер и QA — в разработку, с отчётом `review.md` или `test-report.md`;
- разработчик — в анализ;
- аналитики — в идею;
- DevOps — в разработку или тестирование (только на более ранний этап, чем свой).

Этапы с точки возврата снова считаются не сданными. Три возврата между одной парой этапов —
проблема уходит Решале. Проблему или ограничение роль поднимает `op=escalate` (`reason`, `tried`,
`need`): задача блокируется, и её разбирает агент «Решала» (раздел ниже).

Ворота: ИИ-тимлид (скилл `tt-teamlead`) решает `op=gate decision=approve|return notes=…`. После ворот
«тест → main» задача ждёт кнопки «👤 Одобрить релиз в main» (`op=approve_release`). Только после
неё DevOps делает деплой в main. В удалённый репозиторий сервер ничего не отправляет: это решает владелец.

## Артефакты по ролям

`docs/tasks/<id>/` в ветке задачи:

| Роль | Артефакты |
|---|---|
| PO | `BRD.md` — проблема, пользователи, мировые практики, конкуренты, эффекты, ожидаемые результаты, метрики, границы, риски, не меньше трёх источников |
| Системный аналитик | `SRS.md`, `diagrams.md` (Mermaid), `api.md`, `data-model.md` (оба — если применимо), `RTM.md`, `dev-tasks.md` |
| Архитектор | `HLD.md` (с Mermaid-схемой), `adr/ADR-*.md`, `threats.md`, `poc.md` (если был PoC) |
| Дизайнер | `design/user-flow.md`, `design/ui-spec.md`, `design/handoff.md`, `design/prototype.html` (необязательно) |
| Маркетолог | `marketing/GTM.md`, `media-plan.md`, `briefs.md`, `analytics.md` |
| Разработчик | код, тесты, `MR.md` |
| Ревьюер | `review.md` |
| QA | `test-cases.md`, `test-report.md`, дополненная `RTM.md` |
| DevOps | `runbook.md`, `release-notes.md` |

## Адаптация корпоративных DoR/DoD

Пункты взяты из описания ролей владельца. То, чего в портфеле нет, заменено существующим:

| В описании ролей | Здесь |
|---|---|
| Jira/YouTrack | TaskTreker |
| SonarQube и CI | CI TaskTreker (`tools/ci.py`), см. «CI/CD» ниже |
| Архитектурный комитет и согласование стейкхолдеров | ворота ИИ-тимлида и «да» владельца |
| Тестовый стенд | рабочая копия задачи |
| Figma | описание экранов, состояний и HTML-прототип |

Маркетинговые пункты запуска кампании и отчёта план/факт идут после релиза и вне конвейера —
в DoD это «неприменимо» с причиной. Без команды `verify` у проекта пункты тестов засчитываются
только по доказательству ручной проверки. Ветки деплоя берутся из поля `branches` проекта
(`base`, `test`, `main`), по умолчанию — `разработка`/`develop`, `тестирование`/`test` (создаётся
от main, если её нет), `main`/`master`. Слияния в тестовую ветку и main идут в отдельных рабочих
копиях `<проект>.worktrees/deploy-<ветка>`: выгруженная ветка владельца не меняется.

## CI/CD

Конфигурация — поле `ci` проекта в `projects.json` (ручной слой): шаги `steps` (`name`, `kind` —
install|lint|build|test|e2e|security, `cmd` списком, `cwd`, `on` — task|test|main, `timeout`,
`optional`), развёртывание `deploy.test` и `deploy.main` (`cmd`, `health`), `tag`. Плейсхолдеры:
`{repo}` — основная копия (там `.venv` и инструменты), `{cwd}`, `{base}`, `{test}`, `{main}`,
`{branch}`. Без `ci` берётся прежняя `verify`, без неё — автоопределение (`scripts/check.ps1`,
`check.sh`, Python с тестами, `package.json`, Flutter). Проверить: `py tools/pm.py ci show <проект>`.

| Где | Когда | Что делает |
|---|---|---|
| ветка задачи (`task`) | сдача разработчика и ревью до слияния | шаги с `on: task` |
| тестовая ветка (`test`) | деплой в тест | догоняющее слияние задачи в базовую, базовая → тест, CI, `deploy.test` |
| main (`main`) | деплой в main | возврат прежнего отката, тест → main, CI; красный — откат слияния, задача к разработчику с критическим дефектом; `deploy.main`, тег `release/<дата>-<id>` |

QA подписывает допуск, только если последний прогон CI на тестовой ветке зелёный и сделан на её
текущем коммите. Прогоны — `data/ci.json` (автоматический файл), журналы — `ops/logs/ci/`, на доске —
строка «CI» у карточки (клик — журнал). `py tools/pm.py ci export <проект>` пишет тот же конвейер
в `.github/workflows/tasktreker-ci.yml` репозитория проекта; отправка в GitHub — решение владельца.

## Агент «Решала»: проблемы и эскалации

Тимлид держит только ворота. Проблемы разбирает отдельный агент — «Решала» (скилл `tt-resolver`).

**К нему обращаются:**
- агенты — через `op=escalate`, а не вопросом владельцу. Нет доступа, противоречие, инструмент
  не работает, не получается после двух попыток, нужно решение вне скоупа. Это прописано в каждом
  скилле, в задании сессии и в инструкциях MCP; работает и для задач вне конвейера;
- сервер — в трёх случаях: сессия трижды закончилась без сдачи, DoD не сдан три раза подряд,
  задача трижды вернулась между одной парой этапов.

**Что делает Решала:**
1. Проблема попадает в реестр (`problems`, номер `P-n`), задача блокируется. Решала открывается
   на старшей модели и по возможности **на другом ИИ**, чем агент с проблемой, — свежий взгляд.
2. По паспорту видит проблему, что уже пробовали, журнал и последние запуски. Находит **не меньше
   двух путей решения** с плюсами и минусами. Второе мнение запрашивает у другого ИИ:
   `py tools/pm.py ask <claude|codex> "вопрос"` — запуск только на чтение.
3. Отвечает `op=resolve`:
   - `continue` — роль продолжает с его указаниями: они приходят ей в замечаниях;
   - `return` — задача возвращается на ранний этап;
   - `owner` — нужен владелец. Только когда без него нельзя: права, доступы, деньги, юридическое
     или продуктовое решение.
4. Вопрос владельцу появляется в колокольчике и системным уведомлением. Владелец отвечает
   вариантом из путей решения или своим текстом (`op=answer`, только на доске). Работа продолжается
   с ответом в замечаниях роли.
5. Если Решала сам трижды закончил сессию без решения, проблема уходит владельцу.

### Рецепты сервера и база решений

Механические проблемы до Решалы не доходят (`tools/recipes.py`):

| Рецепт | Проблема | Что делает сервер |
|---|---|---|
| Р1 | нет записи в `.git` | коммитит рабочую копию сам, запуск продолжается |
| Р2 | архитектор или дизайнер без ТЗ | снимает запуск до сдачи аналитика (или даёт пути готового ТЗ) |
| Р3 | сессия трижды без сдачи | сверяет артефакты роли и возвращает её к работе со списком; второй раз — Решале |
| Р4 | «????» вместо текста | правило UTF-8; передача с «????» в артефактах и доказательствах не принимается |
| Р5 | противоречие контрактов | возвращает задачу системному аналитику с матрицей кодов |
| Р6 | обрезанный список задач | `tt_work op=list offset=… limit=…` |

Рецепт срабатывает один раз на запуск: та же проблема повторно — уже к Решале. Решала пополняет базу:
`op=resolve … recipe={title, keywords, instructions}` — запись `К-n` в `workflow.json` → `playbook`; в следующий
раз по всем ключевым словам агенту ответит сервер. Встроенные рецепты перечислены в скилле Решалы
(«Известные решения») и коротко — в скиллах ролей («Известные проблемы»), накопленные — в паспорте Решалы (`known`).

## Колокольчик владельца

Справа вверху, на любой вкладке. Собирает то, что ждёт именно владельца:
- вопросы Решалы;
- релизы в main в пошаговом режиме;
- сбои запуска — например, не найдена командная строка ИИ или окно закрыто, а этап не сдан.

Отвечать можно прямо из списка: вариант, свой ответ, «Одобрить релиз», «Открыть сессию снова».

О каждом новом пункте сервер досок присылает системное уведомление Windows — один раз. При открытой
странице приходит ещё и уведомление браузера, если вы его разрешили. Через MCP ответ владельца,
одобрение релиза и массовый перенос недоступны.

## Дашборд агентов

Вкладка «Дашборд», блок «Агенты», для портфеля и для проекта. Агент — роль конвейера со своим
скиллом, плюс «исполнитель» задач вне конвейера.

| Диаграмма | Что показывает | Источник |
|---|---|---|
| Выполнено задач | Claude и Codex раздельно | запуски роли, закрытые сдачей, возвратом или решением; эскалация не считается |
| Потрачено токенов | токены и деньги агента | сессии запусков роли из журналов Claude и Codex; сессии Codex сопоставляются по папке и времени |
| Предстоит задач | сколько задач ещё пройдёт через агента | этапы впереди и несданные роли текущего этапа, ворота тимлида, проблемы у Решалы; дизайн и маркетинг — «возможно», пока PO не решил |
| Возвраты к агенту | возвраты на его этап и отказы DoD | история конвейера |

В таблице причин возвратов:
- кто возвращал;
- последние причины с номерами задач;
- пункты DoD, которые чаще всего не сданы.

## ИИ, модель и усилия по роли и сложности

Сервер назначает их сам, по таблице `ROUTING` в `tools/pipeline.py`. Её видно в окне «DoR / DoD»
этапа и в скилле каждой роли. Класс модели и усилия указаны для простой / средней / сложной
задачи — по оценке сложности (`complexity.py`).

| Роль | ИИ по порядку | Класс модели | Усилия | Почему |
|---|---|---|---|---|
| Product Owner | Claude → GPT | 3/3/3 | high/high/xhigh | исследование рынка и длинный BRD с источниками |
| Системный аналитик | Claude → GPT | 2/2/3 | medium/high/xhigh | формализация требований без двояких трактовок |
| Solution-архитектор | Claude → GPT | 3/3/3 | high/high/xhigh | архитектура и ADR — всегда старший класс |
| UX/UI-дизайнер | Claude → GPT | 2/2/2 | medium/medium/high | сценарии и спецификация интерфейса |
| Маркетолог | Claude → GPT | 2/2/2 | medium/medium/high | аудитория, позиционирование, тексты |
| Разработчик | GPT → Claude | 1/2/3 | medium/medium/high | код и тесты в нескольких файлах |
| Ревьюер | другой ИИ, чем разработчик | 2/2/3 | high/high/xhigh | перекрёстная проверка |
| QA | GPT → Claude | 2/2/2 | medium/high/high | тест-кейсы, прогоны, регресс |
| DevOps | GPT → Claude | 1/2/2 | medium | runbook и заметки; слияния делает сервер |
| Тимлид | Claude → GPT | 3/3/3 | high/high/xhigh | согласованность всех артефактов |

Модель класса — из линейки ИИ: класс 1 — Haiku или Luna, 2 — Sonnet или Sol, 3 — Opus или Astra.
У Codex усилий выше `high` нет, поэтому `xhigh` у него становится `high`. Роль, закреплённая
владельцем в настройках ролей, сильнее таблицы.

## Кончились токены — задача переходит к другому ИИ

По умолчанию включено: «Кончились токены у ИИ — переводить задачу на другой ИИ».

1. Лимит найден в журнале сессии, или агент сам поставил `op=pause`. Сервер отмечает, что у этого
   ИИ лимит до времени сброса, — это видно плашкой на доске.
2. Если есть следующий ИИ из порядка роли, у которого лимит не исчерпан и есть командная строка:
   - прежний запуск закрывается с пометкой о передаче;
   - новый запуск получает модель и усилия по таблице роли для нового ИИ;
   - в задание добавляется заметка о передаче: точка остановки или указание продолжить с состояния
     рабочей копии — незакоммиченные правки лежат там же;
   - сервер открывает сессию сам, в пределах лимита сессий.
3. Задача вне конвейера тоже передаётся. Новый ИИ работает в ветке прежнего, даже если задача была
   назначена прежнему ИИ.
4. Ждущий, ещё не открытый запуск ИИ, у которого исчерпан лимит, автозапуск не открывает:
   он переводит его на свободный ИИ.
5. Лимит у обоих ИИ — обычная пауза до сброса и продолжение той же сессии.
6. Повтор того же события лимита второй передачи не создаёт. Если процесс прежнего ИИ ещё жив,
   его незакоммиченное сначала уходит WIP-коммитом, затем процесс закрывается. Так в рабочей
   копии всегда один писатель.

### Адаптивный маршрут задачи (TT-109; ТЗ FR-001)

У задачи конвейера есть маршрут: FAST, STANDARD или CRITICAL. Он записан в `pipeline.route`, роль видит
его в паспорте (`task_route`).

- **CRITICAL** — риск high, сложная задача или признак опасной области в тексте, scope или диффе:
  права, оплата, секреты, данные и миграции, публичный API, CI и выпуск, зависимости.
- **FAST** — малая низкорисковая правка, доказанно: есть scope, критерии и тесты, дифф мал и не выходит
  за scope.
- **STANDARD** — всё остальное.

Перед ревью, тестом и релизом маршрут пересчитывается по фактическому диффу и может только подняться.

`adaptive_mode` меняет владелец:
- `shadow` (по умолчанию) — только запись, путь полный;
- `enforce`:
  - FAST пропускает «Идею» и «Анализ» для видов работы из `adaptive_fast_allow`; требования — `why`
    и `acceptance` задачи;
  - CRITICAL ведёт ворота только через тимлида и проверку только независимым ИИ;
  - дифф, вышедший за FAST, возвращает задачу на «Идею».

Посмотреть — `tt_work op=adaptive`.

### Баланс Claude/Codex и восстановление (TT-108; ТЗ FR-015/016)

Выбор ИИ для роли — `provider_balance.choose`. Каждое решение пишется в `provider_decisions`:
кто был пригоден, кто исключён и почему, долг доли, теневой выбор.

- **Режим** складывается из здоровья обоих ИИ:
  - `balanced` — оба доступны;
  - `mono_claude` или `mono_codex` — у второго лимит или нет командной строки;
  - `paused_all` — лимит у обоих.
- **После сброса лимита** ИИ считается восстанавливающимся (`degraded`), а не готовым. Готов он
  после 2 успешных работ с разрывом не меньше минуты и не раньше 3 минут после сброса. Пока
  восстановление не подтверждено, в режиме balanced ему открывается одна пробная сессия.
  Так задачи не бегают туда-обратно.
- **Доли** считаются по принятой работе: сданный этап × уровень сложности, окна 7 и 30 дней,
  только периоды balanced. Меньше 20 событий или 30 единиц — «мало данных», а не перекос.
- **`balance_mode`:**
  - `prefer` (по умолчанию) — прежний порядок роли, баланс считается рядом в тени;
  - `balanced` — выбирается ИИ с наибольшим дефицитом до `target_shares`.

  Закрепление роли владельцем перекрывает баланс, но не лимит.
- **Проверка сложной или рисковой задачи** (уровень 3, риск high или critical) не достаётся
  автору работы. Если независимого ИИ нет, проверка ждёт. Это правило действует всегда.
- **Настройки** меняет только владелец: `balance_mode`, `target_shares`, `affinity_bonus`,
  `role_affinity`. Посмотреть баланс — `tt_work op=balance`.

## Режим согласия владельца

Переключатель «Согласие владельца» в блоке «⚙ Исполнение и ревью» (`op=settings autonomy`).
Сменить его можно только на доске владельца (раздел «Полномочия владельца» ниже).

**Пошаговое** (`step`, по умолчанию):
- каждая сессия — окно; Claude правит файлы рабочей копии без вопросов (`acceptEdits`), команды
  спрашивает; Codex работает в песочнице с вопросами (`on-request`);
- релиз в main — только по кнопке «👤 Одобрить релиз в main»;
- закрытое окно с несданным этапом отмечается на карточке, повторно сессия не открывается.

**Полная автономия** (`full`) — одно согласие, записывается с датой:
- сессии без окон, в фоне; вывод — в `ops/logs/sessions/<запуск>.log`, на доске — «📄 Журнал»;
- Claude: `claude -p --permission-mode auto`. Безопасное классификатор Claude Code разрешает сам,
  опасное отклоняет. Codex: `codex exec --approve-for-me` — песочница рабочей копии
  с автоматической проверкой запросов; `--add-dir` даёт запись в `.git` основного репозитория,
  иначе коммит из рабочей копии задачи не пройдёт;
- агенты не задают вопросов: неясное решают в рамках роли и записывают допущения; проблему —
  к Решале;
- сессия, закончившая ответ без handoff, return, escalate или pause, продолжается автоматически
  (та же сессия, `--resume`). После двух таких продолжений проблема уходит Решале (у задачи вне
  конвейера — провал запуска);
- после ворот тимлида «тест → main» релиз в main выполняется без отдельного «да» — по гранту,
  который выдаётся при включении полной автономии; в журнале тимлида записаны грант и коммит;
- в удалённый репозиторий система не отправляет никогда.

В обоих режимах одновременно открыто не больше `max_sessions` сессий (по умолчанию 4).
Закрытое окно или завершённый процесс места не занимают.

## Полномочия владельца (TT-104; ТЗ TT-U-001: TT3-014, TT3-016, TTU-018)

**Кто владелец.** Права проверяет ядро — `workflow.action(req, origin)`, а не каждый интерфейс
по-своему. Источник `owner` — только доска с токеном владельца (заголовок `X-TaskTreker-Owner`).
Всё остальное — `agent`, и это значение по умолчанию: MCP `tt_work`, CLI `pm.py work`,
HTTP без токена (свой заголовок `X-TaskTreker: 1` поставит и curl агента), любой вызов без источника.
Решения владельца: `settings` (все ключи), `approve_release`, `answer`, `resume_all`,
`to_idea` и `start` не в предпросмотре. Окна ИИ (`/api/launch`), старт проекта и подключение к
ассистентам по HTTP — тоже только с токеном.

**Токен и ключ.** Ключ владельца — `%LOCALAPPDATA%/TaskTreker/owner.key`, вне репозитория и `data/`;
его создаёт сервер досок. Токен доски выводится из ключа. Сервер открывает браузер по ссылке
`…/#owner=<токен>`, страница запоминает токен и убирает его из адреса. Потерян — `pm.py owner-link`
в своём терминале: ссылку команда печатает только человеку (ввод и вывод — консоль), сессии ИИ
получают отказ. Удалить ключ — отозвать токен, все гранты и одобрения разом.

**Одобрение релиза** подписано ключом владельца и содержит `ref` задачи и полный SHA тестовой ветки.
Слияние в main проверяет его дважды: в DoR этапа и в `deploy.run` непосредственно перед `merge`.
Сливается ровно одобренный коммит, а не имя ветки. Отказ без решения владельца:
запись, сделанная руками или до TT-104 (нет подписи), одобрение другой задачи, новый коммит в тесте
после «да» (одобрение снимается, колокольчик спрашивает снова), аварийная остановка.

**Грант полной автономии** выдаётся, когда владелец включает `full`: профиль `local_release`, все проекты,
ветка `main`, срок 30 дней, `external_deploy_allowed: false`. Выключение автономии отзывает грант.
Истёк или подделан — релизы ждут «да», колокольчик показывает «🔑 Грант автономии».

**Аварийная остановка** — `op=stop_all reason=…` (MCP, CLI или «⛔ Стоп» в колокольчике).
Включить может кто угодно: она только запрещает. Открытые запуски получают паузу `kill_switch`
с точкой остановки, незакоммиченное в рабочей копии сохраняется WIP-коммитом, затем сервер
завершает процессы сессий. Пока она включена, запрещены take, claim, enqueue, start, idea,
handoff, ворота, слияния, автозапуск, продолжение пауз и окна ИИ. Работают чтение, план,
pause, cancel, fail и блокировка задач. Снимает остановку только владелец (`resume_all`):
остановленные сессии продолжаются с места остановки той же сессией.

**Версия политики.** Каждое решение владельца — новая `policy.version` в `workflow.json`
с журналом (`policy.log`: что изменилось, кто, хеш итоговой политики). `settings` с `preview=true`
показывает изменение без применения и доступен агенту.

**Окружения.** Команды развёртывания (`ci.deploy.test|main` в `projects.json`) не доверенные:
`projects.json` правят и агенты. Шаг `env_*` выполняет команду, только если владелец одобрил именно её
отпечаток (`settings.environments["проект/окружение"]`, кнопка «👤 Разрешить эту команду» в колокольчике).
Команда изменилась — отпечаток не сходится, развёртывание снова ждёт владельца. Релиз в main также
запрещён при открытом дефекте blocker/critical/major, даже с одобрением.

**Идентификатор операции (TT-105; TT3-017).** Слияния, тег релиза и развёртывание выполняются через
журнал `workflow.json` → `operations` с детерминированным id (`op:<действие>:<задача>:<ветка>:<коммит>`).
Повтор не выполняет действие второй раз. Процесс умер посреди действия — повтор сверяется с Git
(коммит уже в ветке, тег уже стоит) и не сливает второй раз. Развёртывание по Git не проверить —
операция получает `reconciliation_required`, колокольчик «🧩 Сверка операции» спрашивает владельца:
повторить или признать выполненной (`op=reconcile`). Любой изменяющий запрос `tt_work` и HTTP может нести
`operation_id`: повтор возвращает прежний ответ с `replay: true`, другой запрос под тем же id
и одновременный второй отклоняются; права проверяются до кэша ответа.

**Граница.** Агент под той же учётной записью Windows физически может прочитать файл ключа.
Защита рассчитана на ИИ, который действует через штатные интерфейсы, в том числе под влиянием
чужого текста. От намеренного злоумышленника защищает только отдельная учётная запись ОС.

**«▶ Запустить проект»** включает проект в автономную работу. Все ждущие роли конвейера проекта
сервер открывает сам, по мере освобождения мест. «⏸ Остановить проект» снимает это; открытые
сессии доработают свой шаг.

## Лимит токенов: пауза и продолжение с места остановки

Правило в каждом скилле роли, в задании сессии и в инструкциях MCP:

1. Пришло предупреждение, что лимит почти исчерпан, — агент коммитит незавершённое в ветку
   задачи и вызывает `tt_work op=pause ref run worker checkpoint="что сделано, что осталось,
   следующий шаг"` (можно `resets_at`). Запуск и метка остаются за ним, аренда продлена
   до возобновления: задачу никто не перехватит.
2. Лимит оборвал сессию без предупреждения — сервер досок находит отказ в журнале сессии:
   у Claude это строка с `error: rate_limit` и `quotaLimits.resetsAt`, у Codex —
   `usage_limit_exceeded` и время сброса из `rate_limits`. Пауза ставится сама.
3. Возобновление — в момент сброса лимита из журнала плюс 2 минуты; если время сброса
   неизвестно — через 5 часов. Сервер продолжает **ту же сессию**: Claude открывается
   с `--session-id`, продолжается `claude --resume <id>`, Codex — `codex resume <id>`.
   Первая реплика — «лимит восстановлен, продолжай с места остановки» и точка остановки.
   Без идентификатора сессии открывается новая сессия с той же точкой остановки.
4. Пауза и возобновление пишутся в журнал тимлида; на карточке — «⏸ Пауза … возобновление …».
   Если владелец сам написал «продолжай» в окне, первый `heartbeat` снимает паузу.

## Реестр дефектов

- QA, ревьюер и DevOps при возврате регистрируют дефекты: `defects=[{title, severity:
  critical|major|minor, level: unit|integration|e2e|load|manual|static, test}]`. Возврат QA
  без дефектов не принимается.
- Разработчик после возврата сдаёт этап только со способом исправления каждого открытого
  дефекта: `fixes={"D-n": {method, test_level, note}}`. Способ сверяется с коммитами ветки
  после регистрации дефекта:
  - `spec_change` — правились артефакты анализа (SRS, BRD, HLD, API…);
  - `code_to_spec` — правился код;
  - `workaround` — правился код, и есть пояснение не короче 20 символов;
  - `test_fix` — правились файлы тестов; нужен уровень поправленного теста.
- Подпись QA переводит исправленные дефекты в проверенные.

## Метрики работ

`tools/metrics.py` (шаг `pm.py refresh`) пишет `data/metrics.json`. Ничего не оценивает ИИ:
всё считается из журналов сессий, git и истории конвейера.

**Спринт** — окно лимита токенов. Claude пишет время сброса при отказе, Codex — с каждым
отчётом о расходе. Где окна неизвестны, спринт — пятичасовой блок от первой активности.
Окна разных ИИ, наложившиеся друг на друга, — один спринт.

По каждому спринту проекта:
- токены и деньги Claude и Codex раздельно;
- коммиты;
- фичи — закрытые задачи;
- документы — сколько и какие, отдельно ТЗ;
- строки кода и тестов.

По проекту целиком:
- уровни тестов по файлам;
- итоги автопроверок и проверок конвейера, подписи QA;
- правки ТЗ после передачи в разработку и изменения кода по итогам тестирования — на задачу;
- дефекты по способу исправления, уровню, критичности и роли, которая их нашла;
- качество ролей и ИИ:
  - передачи с первой попытки;
  - отказы DoD;
  - возвраты к роли;
  - правки своих артефактов после ворот анализа (отдельно для дизайнера и маркетолога).

Вкладка «Дашборд» показывает метрики. В выпадающем списке — весь портфель (сумма по проектам
и портфельные сигналы) или один проект: графики по спринтам, тесты, правки ТЗ и кода, дефекты,
качество ролей и ИИ. Ссылка ведёт к карточке проекта на вкладке «Проекты».

## Настройки (блок «⚙ Исполнение и ревью» на доске, `op=settings`)

- `auto_pipeline` — открывать сессии ролей автоматически;
- `roles` — какой ИИ ведёт какую роль (`{"developer": "codex", …}`), по умолчанию — ИИ по умолчанию;
- `context_ceiling` — потолок контекста сессии роли для эстафеты (0 или 40–400 тыс. токенов, по умолчанию 90 тыс.);
- прежние `reviewer`, `auto_merge`, `auto_launch_review` — для задач вне конвейера.

## Механизм развития локального разработчика (LEARN)

Опыт разработчика собирается из истории конвейера. Второго источника истины нет:

- каждая сдача разработчика — событие `attempt_submitted`;
- каждый возврат — `attempt_rejected`;
- приёмка — `task_accepted`.

Причину возврата подтверждает машинное доказательство или владелец. Вина модели — только при
выполненных предпосылках. Проверенные карточки опыта попадают в паспорт разработчика (`knowledge`);
исполнитель называет применённые в `handoff.knowledge_applied`. В пилотном проекте разработчик —
`local_mimo`: при недоступном runtime запуск ставится на паузу (`reason=runtime`), к GPT/Claude не
передаётся. Подробно — `docs/МЕХАНИЗМ_РАЗВИТИЯ_АГЕНТА.md`.

## Скиллы

`py tools/pm.py skills build` пересобирает `skills/tt-*/SKILL.md` из спецификации (тест следит за
свежестью). `py tools/pm.py skills install` ставит их в `~/.claude/skills` и `~/.codex/skills`;

## Ограничение спринта поставки

У каждого проекта свой спринт: максимум четыре задачи на всех агентов; задачи других проектов
его не занимают. Новые задачи проекта ждут влития всего его состава в main. Допуск проверяют очередь выбора,
пакетный запуск, принятие роли и диспетчер перед открытием сессии.
Следующая роль и возврат на доработку той же задачи нового места не занимают.
Состав и оставшиеся до main задачи: `pm.py work sprint` / `tt_work op=sprint project=<проект>`;
срез потока одного проекта — `tt_work op=flow project=<проект>`. Режим `rolling` (shadow) по-прежнему
считает `wip_global` на портфель — на исполнение это не влияет.
Подробный контракт и переход уже начатых работ — в `ИСПОЛНЕНИЕ_ЗАДАЧ.md`.

### Поток задач: слот на задачу (TT-106; ТЗ FR-014)

Спринт — режим потока `batch`. Рядом считается режим `rolling` из ТЗ:
- `wip_global` задач на портфель (4) и `wip_per_project` на проект (2);
- выпуск в main освобождает ровно один слот, и сразу можно взять следующую задачу;
- при `prefer_finish` задача с исполнимой поздней стадией запрещает приём новой.
  Поздняя стадия — деплой в main, тестирование или деплой в тест, у которой запуск роли ждёт ресурса.
  Не запрещают: запуск, который уже идёт, запуск на паузе и задача, ждущая «да» владельца.

Учёт один — журнал спринта: слоты лежат в `delivery_sprints.slots`, решения — в `decisions`
(`admit`, `release_complete`, `release_slot`, `block`, `override`) с версией политики.
Повторный приём, смена модели, возврат на доработку и следующая роль второго слота не берут.
Повторно открытая после выпуска задача получает новую заявку (`adm:<ref>:2`).

| Что | Кто | Как |
| --- | --- | --- |
| Режим `batch`/`rolling`, `wip_global`, `wip_per_project`, `prefer_finish`, `blocked_exception_limit` | владелец | `op=settings` на доске |
| Закрыть слот без выпуска (отменена, брошена) | владелец | `op=release_slot` (ref, reason) |
| Исключение `critical_incident`/`owner_override` — мимо лимита на приёме; `blocked_slot` — не считать слот заблокированной задачи | владелец | `op=flow_exception` (ref, kind, reason, expires_at ≤ 30 дней) |
| Внешняя блокировка: видна, слот не освобождает; просроченная перепроверка — в колокольчике | любой | `op=flow_block` (ref, reason, responsible, recheck_at) / `op=flow_unblock` |
| Снимок: слоты, стадии, возраст, блокировки, причины запрета, кандидаты на завершение, shadow-отличия | любой | `op=flow`, на доске — строка «Поток» |

Пока действует `batch`, в shadow виден вердикт `rolling`: `op=flow` → `divergences`.
Переключать режим стоит после того, как отличия разобраны. Исключение и закрытие слота
влияют только на приём: CI, ворота, DoD и одобрение релиза остаются прежними.
