# Механизм развития локального ИИ-разработчика (LEARN-01…09)

Источник: ТЗ «Механизм развития MiMo V2.6 9B», задачи TT-110…TT-119, корень
`mem-zapros-mehanizm-nakopleniy-c98157`. Главный принцип — **ADR-LEARN-001 «Evidence-first learning»**:
измерить результат → установить подтверждённую причину → исправить контекст или процесс →
сохранить проверенное знание → измерить ещё раз → и только при доказанной необходимости,
решением владельца, отдельно рассмотреть обучение весов.

Механизм **ничего не обучает и не меняет веса**. В коде нет функций обучения, автоматического
продвижения и кнопки «Обучить ИИ».

## 1. Карта интеграции (LEARN-01)

Новой второй системы нет: каждый факт берётся из уже существующего источника, механизм хранит
только производные события со ссылками.

| Что нужно механизму | Источник истины (не дублируется) | Как используется |
| --- | --- | --- |
| Попытка разработчика, возврат, приёмка | `workflow.json` → `tasks.*.pipeline.history` (handoff, return, проверки) | `learning_events.derive` переводит историю в события; `event_id` — хеш источника, повтор ничего не добавляет |
| Модель, усилия, конфигурация | запуск (`runs[]`: agent, model, `learning.model_config_id`) | `model_config_of(run)`; смена GGUF, квантования или промпта даёт новый `model_config_id` (AT-10) |
| Ревизия ТЗ | паспорт задачи (`acceptance`, `why`, `spec_ref`) | `spec_revision(t)` — хеш; после первой сдачи изменённое ТЗ даёт `requirement_change` (AT-04) |
| Дефекты, CI, тесты | `defects`/`fixes` конвейера, `ci.json` | ссылки `defect:`, `ci:`, `test:` — машинные доказательства причин |
| Метрики ролей | `metrics.py` | не трогаются; LEARN считает только пилот разработчика (M01–M11) |
| Знание | `data/memory/*.md` (`memory.py`) | карточка опыта — обычная запись вида «решение» с полем `learning` |
| Решение о процессе и обучении | журнал learning (`decision_recorded`, `decision_status`) | статусы владельца не запускают ничего |

Миграции данных нет: новое хранилище `data/learning/` только добавляется; `projects.json`,
память, дерево, финансы и доски не переписываются (AT-16). Отключить сбор опыта можно настройкой
`learning.enabled=false`, задачи при этом выполняются как обычно (§15.5).

### Встраивание в конвейер

- **Пилот:** `settings.learning.pilot_projects`. В пилотном проекте роль разработчика назначается
  только `local_mimo` (`orchestra.role_agent`) — без баланса Claude/Codex и без failover. Остальные
  роли (ревью, QA, DevOps) и все прочие проекты работают как раньше. `local_mimo` не входит в
  `PROVIDERS`, поэтому баланс 50/50 по принятой работе он не искажает.
- **Запуск разработчика** (`workflow.start_run`): в запуск пишутся `model_config_id`, ревизия ТЗ,
  хеш паспорта и выданные карточки (только ссылки).
- **Сдача** (`orchestra.handoff`): ревизия кода и `knowledge_applied` — какие карточки исполнитель
  назвал применёнными.
- **Сервер досок** раз в 5 минут синхронизирует журнал и предлагает причины новым возвратам
  (`serve.learn_once`). Сбой аналитики работу не останавливает.
- **Резервная копия** (`pm.py backup`) включает `data/learning/`. В git каталог не попадает: он в
  `.gitignore`, тест это держит.

## 3. Команды (ТЗ §12.3)

```bash
py tools/pm.py learn status [--project P] [--model-config ID] [--since ISO]
py tools/pm.py learn report --project P            # отчёт с n, пропусками и ссылками
py tools/pm.py learn returns --cause model_logic_error --confirmed yes
py tools/pm.py learn inspect <проект/id>           # все попытки задачи и их причины
py tools/pm.py learn classify --event evt_… --cause environment_failure --evidence ci:CI-12
py tools/pm.py learn knowledge candidates | propose … | verify <id> | reject <id> --why "…"
py tools/pm.py learn training-gate [--project P]   # рекомендация, обучения нет
py tools/pm.py learn models | model-register cfg.json | model-activate <id>
py tools/local_mimo.py health | agent <проект/id> <RUN>   # runtime и исполнение запуска
```

**Права.** Читать, синхронизировать, предлагать причину и карточку может любой источник. Остальное
делает только владелец (доска по ссылке владельца или его терминал):

- подтверждение и отклонение карточки;
- статус рекомендации;
- регистрация и активация конфигурации модели;
- регистрация набора оценки.

Агент подтверждает причину только машинным доказательством: `ci:`, `test:`, `defect:`, `repro:`.

## 4. Что проверено и что нельзя проверить без железа

Тесты `tests/test_learning.py` (AT-01…AT-20) работают без GPU. Локальная модель там подменена
mock-сервером OpenAI-совместимого API. Пройденный тест доказывает, что **механизм работает**:
события, причины, метрики, права, карточки, ворота, отсутствие failover и вычистка секретов.
Экономию и качество он **не доказывает**.

**LEARN-10 (TT-119)** остаётся открытой рабочей серией. Нужны:

- реальная GGUF-сборка MiMo-V2.6-9B на ПК владельца (llama.cpp или аналог на `127.0.0.1`);
- 50 принятых задач пилотного проекта.

Только тогда метрики выйдут из статуса `insufficient_data`, и владелец примет задокументированное
решение: менять процесс, контекст, пока обходиться без LoRA или ставить эксперимент. Заявлять об
улучшении до этого нельзя (§18).
