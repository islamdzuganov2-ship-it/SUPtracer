# Конвейер задач: от идеи до main

Доска «Доски задач» — это конвейер из семи этапов. У каждого этапа есть роли-агенты,
DoR (условия, чтобы роли взяли задачу) и DoD (условия, чтобы сдать этап). Всё это
задано данными в `tools/pipeline.py`: по ним проверяет сервер, из них собраны скиллы
ролей (`skills/tt-*`), их показывает доска (кнопка «DoR / DoD» в заголовке колонки).

| Этап | Роли | Ворота |
|---|---|---|
| Идея | Product Owner | — |
| Анализ | Системный аналитик, Solution-архитектор; UX/UI-дизайнер и маркетолог — если их решил подключить PO | ИИ-тимлид: «анализ → разработка» |
| Разработка | Разработчик | — |
| Ревью | Ревьюер | — |
| Деплой в тест | DevOps-инженер | — |
| Тестирование | QA-инженер | ИИ-тимлид: «тест → main» |
| Деплой в main | DevOps-инженер | «Да» владельца |

Порядок «сначала деплой в тест, потом тестирование» — решение владельца 31.10.2026: QA проверяет
развёрнутую тестовую ветку (паспорт QA, поле `test_env`: ветка, рабочая копия, последний прогон
CI), а в main уходит только то, что прошло тестирование без открытых дефектов.

«Отменено» — восьмая колонка. Задачи вне конвейера (заведённые до него или формой
«＋ Новая задача») стоят в колонке по своему статусу: готовые — в «Деплой в main»,
непроработанные — в «Идея», в работе — в «Разработка», на проверке — в «Ревью».

## Как задача попадает в конвейер

- Из терминала Claude Code или Codex: ассистент вызывает `tt_work op=idea project=… title=… text=… source=claude|codex`.
- С доски: кнопка «💡 Идея».
- Из командной строки: `py tools/pm.py idea <проект> "название" --text "что и зачем"`.

Идея становится задачей в «Идея» с исходным запросом в памяти проекта. Сразу создаётся
рабочая копия задачи `<проект>.worktrees/task-<id>` с веткой `task/<id>`: в ней роли
пишут артефакты (`docs/tasks/<id>/`) и код — всё едет одной веткой до main.

## Как работает оркестрация

Тимлид-оркестратор — сервер (`tools/orchestra.py`):

1. Проверяет DoR этапа. Не выполнен — задача ждёт с причиной на карточке, событие в журнале тимлида.
2. Ставит запуски ролям этапа. Сервер досок открывает их сессии сам, если включено «Конвейер:
   открывать сессии ролей автоматически». Сессия — окно Claude Code или Codex на модели роли (не ниже
   её класса: PO и архитектор — старший), со скиллом роли и правом правки файлов в рабочей копии
   (Claude — `acceptEdits`, Codex — `workspace-write`). Команды подтверждает владелец.
3. Роль сдаёт работу `op=handoff` со списком пунктов DoD. Это и есть уведомление тимлиду: событие
   уходит в журнал. Сервер проверяет пункты:
   - артефакт закоммичен в ветку задачи, есть все разделы-заголовки, нужный размер;
   - доказательство не короче 20 символов;
   - машинные пункты: ссылки на источники, диаграммы, таблицы, открытые дефекты, коммиты,
     слияние без конфликтов, секреты, тесты.

   Не выполнен хоть один пункт — передача не принимается, запуск остаётся у роли со списком `failed`.
   «Неприменимо» допустимо только там, где это разрешено, и с причиной.
4. Тяжёлые пункты — прогоны CI, слияние в базовую ветку на ревью, деплой в тестовую
   ветку и в main — выполняются фоновым заданием (журнал `ops/logs/pipeline.log`). Провал возвращает
   задачу той же роли с замечаниями. После трёх провалов подряд — проблема уходит Решале.
5. Все роли этапа сдали работу → ворота, если есть → этап сдан → DoR следующего этапа.

Назад задачу возвращают `op=return`:
- ревьюер и QA — в разработку, с отчётом `review.md` или `test-report.md`;
- разработчик — в анализ;
- аналитики — в идею;
- DevOps — в разработку или тестирование (только на более ранний этап, чем свой).

Этапы с точки возврата снова считаются не сданными. Три возврата между одной парой этапов —
проблема уходит Решале. Проблему или ограничение роль поднимает `op=escalate` (`reason`, `tried`,
`need`): задача блокируется, и её разбирает агент «Решала» (раздел ниже).

Ворота: ИИ-тимлид (скилл `tt-teamlead`) решает `op=gate decision=approve|return notes=…`. После ворот
«тест → main» задача ждёт кнопки «👤 Одобрить релиз в main» (`op=approve_release`). Только после
неё DevOps делает деплой в main. В удалённый репозиторий сервер ничего не отправляет: это решает владелец.

## Адаптация корпоративных DoR/DoD

Пункты взяты из описания ролей владельца. То, чего в портфеле нет, заменено существующим:

| В описании ролей | Здесь |
|---|---|
| Jira/YouTrack | TaskTreker |
| SonarQube и CI | CI TaskTreker (`tools/ci.py`), см. «CI/CD» ниже |
| Архитектурный комитет и согласование стейкхолдеров | ворота ИИ-тимлида и «да» владельца |
| Тестовый стенд | рабочая копия задачи |
| Figma | описание экранов, состояний и HTML-прототип |

Маркетинговые пункты запуска кампании и отчёта план/факт идут после релиза и вне конвейера —
в DoD это «неприменимо» с причиной. Без команды `verify` у проекта пункты тестов засчитываются
только по доказательству ручной проверки. Ветки деплоя берутся из поля `branches` проекта
(`base`, `test`, `main`), по умолчанию — `разработка`/`develop`, `тестирование`/`test` (создаётся
от main, если её нет), `main`/`master`. Слияния в тестовую ветку и main идут в отдельных рабочих
копиях `<проект>.worktrees/deploy-<ветка>`: выгруженная ветка владельца не меняется.

## CI/CD

Конфигурация — поле `ci` проекта в `projects.json` (ручной слой): шаги `steps` (`name`, `kind` —
install|lint|build|test|e2e|security, `cmd` списком, `cwd`, `on` — task|test|main, `timeout`,
`optional`), развёртывание `deploy.test` и `deploy.main` (`cmd`, `health`), `tag`. Плейсхолдеры:
`{repo}` — основная копия (там `.venv` и инструменты), `{cwd}`, `{base}`, `{test}`, `{main}`,
`{branch}`. Без `ci` берётся прежняя `verify`, без неё — автоопределение (`scripts/check.ps1`,
`check.sh`, Python с тестами, `package.json`, Flutter). Проверить: `py tools/pm.py ci show <проект>`.

| Где | Когда | Что делает |
|---|---|---|
| ветка задачи (`task`) | сдача разработчика и ревью до слияния | шаги с `on: task` |
| тестовая ветка (`test`) | деплой в тест | догоняющее слияние задачи в базовую, базовая → тест, CI, `deploy.test` |
| main (`main`) | деплой в main | возврат прежнего отката, тест → main, CI; красный — откат слияния, задача к разработчику с критическим дефектом; `deploy.main`, тег `release/<дата>-<id>` |

QA подписывает допуск, только если последний прогон CI на тестовой ветке зелёный и сделан на её
текущем коммите. Прогоны — `data/ci.json` (автоматический файл), журналы — `ops/logs/ci/`, на доске —
строка «CI» у карточки (клик — журнал). `py tools/pm.py ci export <проект>` пишет тот же конвейер
в `.github/workflows/tasktreker-ci.yml` репозитория проекта; отправка в GitHub — решение владельца.

## Агент «Решала»: проблемы и эскалации

Тимлид держит только ворота. Проблемы разбирает отдельный агент — «Решала» (скилл `tt-resolver`).

**К нему обращаются:**
- агенты — через `op=escalate`, а не вопросом владельцу. Нет доступа, противоречие, инструмент
  не работает, не получается после двух попыток, нужно решение вне скоупа. Это прописано в каждом
  скилле, в задании сессии и в инструкциях MCP; работает и для задач вне конвейера;
- сервер — в трёх случаях: сессия трижды закончилась без сдачи, DoD не сдан три раза подряд,
  задача трижды вернулась между одной парой этапов.

**Что делает Решала:**
1. Проблема попадает в реестр (`problems`, номер `P-n`), задача блокируется. Решала открывается
   на старшей модели и по возможности **на другом ИИ**, чем агент с проблемой, — свежий взгляд.
2. По паспорту видит проблему, что уже пробовали, журнал и последние запуски. Находит **не меньше
   двух путей решения** с плюсами и минусами. Второе мнение запрашивает у другого ИИ:
   `py tools/pm.py ask <claude|codex> "вопрос"` — запуск только на чтение.
3. Отвечает `op=resolve`:
   - `continue` — роль продолжает с его указаниями: они приходят ей в замечаниях;
   - `return` — задача возвращается на ранний этап;
   - `owner` — нужен владелец. Только когда без него нельзя: права, доступы, деньги, юридическое
     или продуктовое решение.
4. Вопрос владельцу появляется в колокольчике и системным уведомлением. Владелец отвечает
   вариантом из путей решения или своим текстом (`op=answer`, только на доске). Работа продолжается
   с ответом в замечаниях роли.
5. Если Решала сам трижды закончил сессию без решения, проблема уходит владельцу.

## Колокольчик владельца

Справа вверху, на любой вкладке. Собирает то, что ждёт именно владельца:
- вопросы Решалы;
- релизы в main в пошаговом режиме;
- сбои запуска — например, не найдена командная строка ИИ или окно закрыто, а этап не сдан.

Отвечать можно прямо из списка: вариант, свой ответ, «Одобрить релиз», «Открыть сессию снова».

О каждом новом пункте сервер досок присылает системное уведомление Windows — один раз. При открытой
странице приходит ещё и уведомление браузера, если вы его разрешили. Через MCP ответ владельца,
одобрение релиза и массовый перенос недоступны.

## Дашборд агентов

Вкладка «Дашборд», блок «Агенты», для портфеля и для проекта. Агент — роль конвейера со своим
скиллом, плюс «исполнитель» задач вне конвейера.

| Диаграмма | Что показывает | Источник |
|---|---|---|
| Выполнено задач | Claude и Codex раздельно | запуски роли, закрытые сдачей, возвратом или решением; эскалация не считается |
| Потрачено токенов | токены и деньги агента | сессии запусков роли из журналов Claude и Codex; сессии Codex сопоставляются по папке и времени |
| Предстоит задач | сколько задач ещё пройдёт через агента | этапы впереди и несданные роли текущего этапа, ворота тимлида, проблемы у Решалы; дизайн и маркетинг — «возможно», пока PO не решил |
| Возвраты к агенту | возвраты на его этап и отказы DoD | история конвейера |

В таблице причин возвратов:
- кто возвращал;
- последние причины с номерами задач;
- пункты DoD, которые чаще всего не сданы.

## ИИ, модель и усилия по роли и сложности

Сервер назначает их сам, по таблице `ROUTING` в `tools/pipeline.py`. Её видно в окне «DoR / DoD»
этапа и в скилле каждой роли. Класс модели и усилия указаны для простой / средней / сложной
задачи — по оценке сложности (`complexity.py`).

| Роль | ИИ по порядку | Класс модели | Усилия | Почему |
|---|---|---|---|---|
| Product Owner | Claude → GPT | 3/3/3 | high/high/xhigh | исследование рынка и длинный BRD с источниками |
| Системный аналитик | Claude → GPT | 2/2/3 | medium/high/xhigh | формализация требований без двояких трактовок |
| Solution-архитектор | Claude → GPT | 3/3/3 | high/high/xhigh | архитектура и ADR — всегда старший класс |
| UX/UI-дизайнер | Claude → GPT | 2/2/2 | medium/medium/high | сценарии и спецификация интерфейса |
| Маркетолог | Claude → GPT | 2/2/2 | medium/medium/high | аудитория, позиционирование, тексты |
| Разработчик | GPT → Claude | 1/2/3 | medium/medium/high | код и тесты в нескольких файлах |
| Ревьюер | другой ИИ, чем разработчик | 2/2/3 | high/high/xhigh | перекрёстная проверка |
| QA | GPT → Claude | 2/2/2 | medium/high/high | тест-кейсы, прогоны, регресс |
| DevOps | GPT → Claude | 1/2/2 | medium | runbook и заметки; слияния делает сервер |
| Тимлид | Claude → GPT | 3/3/3 | high/high/xhigh | согласованность всех артефактов |

Модель класса — из линейки ИИ: класс 1 — Haiku или Luna, 2 — Sonnet или Sol, 3 — Opus или Astra.
У Codex усилий выше `high` нет, поэтому `xhigh` у него становится `high`. Роль, закреплённая
владельцем в настройках ролей, сильнее таблицы.

## Кончились токены — задача переходит к другому ИИ

По умолчанию включено: «Кончились токены у ИИ — переводить задачу на другой ИИ».

1. Лимит найден в журнале сессии, или агент сам поставил `op=pause`. Сервер отмечает, что у этого
   ИИ лимит до времени сброса, — это видно плашкой на доске.
2. Если есть следующий ИИ из порядка роли, у которого лимит не исчерпан и есть командная строка:
   - прежний запуск закрывается с пометкой о передаче;
   - новый запуск получает модель и усилия по таблице роли для нового ИИ;
   - в задание добавляется заметка о передаче: точка остановки или указание продолжить с состояния
     рабочей копии — незакоммиченные правки лежат там же;
   - сервер открывает сессию сам, в пределах лимита сессий.
3. Задача вне конвейера тоже передаётся. Новый ИИ работает в ветке прежнего, даже если задача была
   назначена прежнему ИИ.
4. Ждущий, ещё не открытый запуск ИИ, у которого исчерпан лимит, автозапуск не открывает:
   он переводит его на свободный ИИ.
5. Лимит у обоих ИИ — обычная пауза до сброса и продолжение той же сессии.

## Режим согласия владельца

Переключатель «Согласие владельца» в блоке «⚙ Исполнение и ревью» (`op=settings autonomy`).
Сменить его можно только на доске: через MCP ИИ этого сделать не может. Через MCP недоступны
и другие решения владельца: одобрение релиза, массовый перенос в «Идея», лимит сессий, автослияние.

**Пошаговое** (`step`, по умолчанию):
- каждая сессия — окно; Claude правит файлы рабочей копии без вопросов (`acceptEdits`), команды
  спрашивает; Codex работает в песочнице с вопросами (`on-request`);
- релиз в main — только по кнопке «👤 Одобрить релиз в main»;
- закрытое окно с несданным этапом отмечается на карточке, повторно сессия не открывается.

**Полная автономия** (`full`) — одно согласие, записывается с датой:
- сессии без окон, в фоне; вывод — в `ops/logs/sessions/<запуск>.log`, на доске — «📄 Журнал»;
- Claude: `claude -p --permission-mode auto`. Безопасное классификатор Claude Code разрешает сам,
  опасное отклоняет. Codex: `codex exec --approve-for-me` — песочница рабочей копии
  с автоматической проверкой запросов; `--add-dir` даёт запись в `.git` основного репозитория,
  иначе коммит из рабочей копии задачи не пройдёт;
- агенты не задают вопросов: неясное решают в рамках роли и записывают допущения; проблему —
  к Решале;
- сессия, закончившая ответ без handoff, return, escalate или pause, продолжается автоматически
  (та же сессия, `--resume`). После двух таких продолжений проблема уходит Решале (у задачи вне
  конвейера — провал запуска);
- после ворот тимлида «тест → main» релиз в main выполняется без отдельного «да»; в журнале
  тимлида записано, по какому согласию;
- в удалённый репозиторий система не отправляет никогда.

В обоих режимах одновременно открыто не больше `max_sessions` сессий (по умолчанию 4).
Закрытое окно или завершённый процесс места не занимают.

**«▶ Запустить проект»** включает проект в автономную работу. Все ждущие роли конвейера проекта
сервер открывает сам, по мере освобождения мест. «⏸ Остановить проект» снимает это; открытые
сессии доработают свой шаг.

## Лимит токенов: пауза и продолжение с места остановки

Правило в каждом скилле роли, в задании сессии и в инструкциях MCP:

1. Пришло предупреждение, что лимит почти исчерпан, — агент коммитит незавершённое в ветку
   задачи и вызывает `tt_work op=pause ref run worker checkpoint="что сделано, что осталось,
   следующий шаг"` (можно `resets_at`). Запуск и метка остаются за ним, аренда продлена
   до возобновления: задачу никто не перехватит.
2. Лимит оборвал сессию без предупреждения — сервер досок находит отказ в журнале сессии:
   у Claude это строка с `error: rate_limit` и `quotaLimits.resetsAt`, у Codex —
   `usage_limit_exceeded` и время сброса из `rate_limits`. Пауза ставится сама.
3. Возобновление — в момент сброса лимита из журнала плюс 2 минуты; если время сброса
   неизвестно — через 5 часов. Сервер продолжает **ту же сессию**: Claude открывается
   с `--session-id`, продолжается `claude --resume <id>`, Codex — `codex resume <id>`.
   Первая реплика — «лимит восстановлен, продолжай с места остановки» и точка остановки.
   Без идентификатора сессии открывается новая сессия с той же точкой остановки.
4. Пауза и возобновление пишутся в журнал тимлида; на карточке — «⏸ Пауза … возобновление …».
   Если владелец сам написал «продолжай» в окне, первый `heartbeat` снимает паузу.

## Реестр дефектов

- QA, ревьюер и DevOps при возврате регистрируют дефекты: `defects=[{title, severity:
  critical|major|minor, level: unit|integration|e2e|load|manual|static, test}]`. Возврат QA
  без дефектов не принимается.
- Разработчик после возврата сдаёт этап только со способом исправления каждого открытого
  дефекта: `fixes={"D-n": {method, test_level, note}}`. Способ сверяется с коммитами ветки
  после регистрации дефекта:
  - `spec_change` — правились артефакты анализа (SRS, BRD, HLD, API…);
  - `code_to_spec` — правился код;
  - `workaround` — правился код, и есть пояснение не короче 20 символов;
  - `test_fix` — правились файлы тестов; нужен уровень поправленного теста.
- Подпись QA переводит исправленные дефекты в проверенные.

## Метрики работ

`tools/metrics.py` (шаг `pm.py refresh`) пишет `data/metrics.json`. Ничего не оценивает ИИ:
всё считается из журналов сессий, git и истории конвейера.

**Спринт** — окно лимита токенов. Claude пишет время сброса при отказе, Codex — с каждым
отчётом о расходе. Где окна неизвестны, спринт — пятичасовой блок от первой активности.
Окна разных ИИ, наложившиеся друг на друга, — один спринт.

По каждому спринту проекта:
- токены и деньги Claude и Codex раздельно;
- коммиты;
- фичи — закрытые задачи;
- документы — сколько и какие, отдельно ТЗ;
- строки кода и тестов.

По проекту целиком:
- уровни тестов по файлам;
- итоги автопроверок и проверок конвейера, подписи QA;
- правки ТЗ после передачи в разработку и изменения кода по итогам тестирования — на задачу;
- дефекты по способу исправления, уровню, критичности и роли, которая их нашла;
- качество ролей и ИИ:
  - передачи с первой попытки;
  - отказы DoD;
  - возвраты к роли;
  - правки своих артефактов после ворот анализа (отдельно для дизайнера и маркетолога).

Вкладка «Дашборд» показывает метрики. В выпадающем списке — весь портфель (сумма по проектам
и портфельные сигналы) или один проект: графики по спринтам, тесты, правки ТЗ и кода, дефекты,
качество ролей и ИИ. Ссылка ведёт к карточке проекта на вкладке «Проекты».

## Настройки (блок «⚙ Исполнение и ревью» на доске, `op=settings`)

- `auto_pipeline` — открывать сессии ролей автоматически;
- `roles` — какой ИИ ведёт какую роль (`{"developer": "codex", …}`), по умолчанию — ИИ по умолчанию;
- прежние `reviewer`, `auto_merge`, `auto_launch_review` — для задач вне конвейера.

## Скиллы

`py tools/pm.py skills build` пересобирает `skills/tt-*/SKILL.md` из спецификации (тест следит за
свежестью). `py tools/pm.py skills install` ставит их в `~/.claude/skills` и `~/.codex/skills`;
`pm.py connect` делает это сам. Чужие скиллы с теми же именами не перезаписываются.
