## 1. Цель и сценарии

Владелец, разработчик и агент должны находить точный фрагмент ТЗ, связанный участок кода и доказательство реализации без чтения полного комплекта документов или всего репозитория. Результат поиска показывает короткую объяснимую цепочку, предлагает открыть конкретный фрагмент и указывает, чего не хватает для вывода.

| Сценарий | Вход | Ожидаемый результат |
|---|---|---|
| Найти правило | «Когда можно брать следующую задачу?» | Действующий раздел регламента, связанные требования и реализация проверки очереди. |
| Проверить реализацию | Идентификатор `C-10` и проект | Точный пункт чек-листа, редакция ТЗ, файлы демо и рабочего UI с указанием роли, привязанные тесты, статус доказательств. |
| Оценить влияние | Раздел ТЗ, символ или diff | Затронутые компоненты, требования и проверки с путями связей. Отдельно показать гипотезы. |
| Подготовить работу агента | `task_ref`, `spec_ref`, область файлов и текущая ревизия | Малый пакет точных фрагментов в бюджете токенов с возможностью раскрыть источники. |
| Разобрать противоречие | Две действующие формулировки лимита | Оба фрагмента, их применимость, причина конфликта, статус редакций. Выбор приоритета по утверждённым правилам. |

Продуктовый минимум включает локальный индекс по проекту, поиск и чтение фрагментов, четыре направления навигации, привязку к задаче и контроль полноты доказательств. Полный режим добавляет PDF, скриншоты и схемы, семантические предложения, отчёты по кластерам и анализ изменений.


### 1.1. Обязательный принцип: сначала существующая система, затем изменения

**Первое включение функции НЕ предполагает пустой граф.** Система обязана анализировать *уже существующие* и доступные на момент запуска код, документы, чек-листы, конфигурации, задачи, тесты и подтверждения. Она строит исходные графы по фактическим данным, а не ждёт будущих коммитов и новых документов. Нельзя считать внедрение завершённым, если индексатор умеет строить граф только по вновь созданным файлам.

- **Источники истины не изменяются:** индексация создаёт производный индекс, не переписывает документы, не реорганизует папки, не вставляет ID в код и не изменяет статусы задач.
- **Первый снимок воспроизводим:** фиксируются Git SHA, `worktree/dirty`, версии внешних документов, перечень всех просмотренных источников, версии парсеров, профили доступа и правила исключений.
- **Индекс без охвата не принимается:** до публикации известны состав доступного корпуса, успешно разобранные единицы, пропущенные единицы и причины пропусков. «Связь не найдена» нельзя приравнивать к «реализация отсутствует».
- **Построение по всем четырём направлениям:** D1–D4 получаются из общего типизированного набора узлов/рёбер. Отображаемые D3 и D4 — связанные проекции, а не две противоречащие друг другу базы.
- **Двухуровневая готовность:** `text_code_baseline_ready` после индексации всех доступных поддерживаемых текстовых и кодовых источников; `full_corpus_baseline_ready` после обработки всех предусмотренных подключённых форматов, включая PDF/изображения, либо после явной фиксации неподдерживаемых и исключённых единиц с указанием неполного покрытия.
- **Граф всегда объясним:** каждое подтверждённое ребро ведёт к исходному месту; гипотезы, коллизии и неизвестность выделены отдельно.

### 1.2. Обязательные результаты первого запуска

1. `SOURCE_INVENTORY.json` — машинно-читаемый реестр охваченных, пропущенных, исключённых и недоступных источников с причинами.
2. `GRAPH_BASELINE.json` — паспорт исходного снимка, точные версии, охват, статистика по узлам, рёбрам и направлениям D1–D4.
3. `GRAPH_REPORT.md` — понятный человеку отчёт по текущей архитектуре, требованиям, связям, кластерам, хабам, несоответствиям, устаревшим редакциям, пробелам покрытия и доказательствам.
4. **Интерактивный граф в интерфейсе** — минимум обзор по модулям/доменам, D1–D4 по выбранному узлу, фильтры и переход к точному источнику. При невозможности отобразить полный граф без перегрузки — иерархическая свёртка и подгрузка окружения, а не отбрасывание данных.
5. **Регистр проблем `GRAPH_FINDINGS.json`** — наблюдения отдельно от выводов о дефектах: `unlinked_requirement`, `undocumented_component`, `missing_test_evidence`, `contradiction_candidate`, `superseded_reference`, `unresolved_link`, `orphan_component`, `index_gap`.
6. **Историческая точка сравнения** — защищённый от случайной перезаписи `baseline_snapshot_id` и команда сравнения будущих состояний с базовым графом.

При отсутствии фактических данных для отдельного типа отношений публикуется ноль подтверждённых связей и статус покрытия, а не вымышленные рёбра. Отчёт не объявляет функцию реализованной только на основании похожих названий.

### 1.3. Границы ответственности и режимы

- `initial_bootstrap` — полный первоначальный проход согласованного и разрешённого корпуса текущего проекта.
- `incremental_sync` — обработка изменений исходных файлов, документов, задач, тестов и ревизий после базового снимка.
- `clean_rebuild` — пересоздание производного индекса из зафиксированных источников и правил, без потери вручную подтверждённых решений.
- `historical_compare` — сравнение двух снимков с учётом версии и прав.
- `read_only_research` — поиск и визуализация без изменения оригиналов.

**Не входит без отдельного требования:** автоматическое исправление кода/документов, утверждение противоречащих регламентов, признание требования исполненным без доказательств, бесконтрольная индексация всех удалённых веток/внешних аккаунтов и автоматическая отправка приватного содержимого во внешнюю LLM.

## 2. Четыре измерения графа

Граф типизированный. «Четыре измерения» в этом ТЗ — четыре направления связей между двумя предметными слоями. Ревизия и применимость являются атрибутами каждого направления. Задачи, проверки и запуски связывают граф с конвейером.

| Направление | Канонические отношения | Запросы |
|---|---|---|
| **D1. Документ → документ** | `references`, `refines`, `supersedes`, `contradicts`, `duplicates` | Где описан следующий уровень детализации? Какой пункт заменён? Какие правила конфликтуют? |
| **D2. Код → код** | `imports`, `calls`, `implements_interface`, `reads`, `writes`, `handles` | Кто вызывает компонент? Где поток данных меняется? Какие клиенты затронет diff? |
| **D3. Документ → код** | `implemented_by`, `configured_by`, `verified_by`, `illustrated_by` | Где реализовано требование? Какой тест проверяет критерий? Где находится прототип? |
| **D4. Код → документ** | Обратные представления D3 и самостоятельное `documented_in` для явно указанной кодом документации | Какое требование объясняет эту проверку? Где описан внешний контракт? Какие блоки ТЗ затрагивает изменение символа? |

Обратный проход использует один ID ребра с обратным отображаемым отношением. `implements` и `implemented_by` в этом случае ссылаются на одну запись. Самостоятельная ссылка из комментария на руководство создаёт `documented_in`, если комментарий устанавливает именно справочную связь. Тип `illustrated_by` исключён из маршрута доказательства реализации.

**Внешние связи:** `Task addresses Requirement`, `Task touches CodeComponent`, `Run executes TestCase`, `Run validates AcceptanceCriterion`, `Run built_from Commit`. `touches` можно получить из фактического diff. Закрытие задачи само по себе не устанавливает прохождение теста или выпуск.


### 2.1. Проекции, уровень детализации и типы связей

Система хранит **один нормализованный типизированный граф** и выдаёт четыре предметные проекции. Представление D4 не создаёт второй набор дублирующих обратных рёбер D3. Узлы должны связываться на уровне *конкретных фрагментов реализации*: раздел ТЗ → требование → критерий → функция/класс/API/конфигурация → тест → запуск/коммит. Для обзора узлы агрегируются в домены/компоненты; при раскрытии возвращаются первичные блоки без потери идентичности.

Обязательные уровни визуализации: `project → subsystem/domain → module/document → block/requirement → symbol/criterion → evidence`. Всякая агрегированная связь хранит число подтверждённых, предположительных и спорных исходных связей, но сама по себе не становится доказательством реализации. Для задач изменения кода граф умеет идти в обе стороны и восстанавливать цепочку влияния.

Правила семантики:

- `references` означает явную ссылку; `refines` — действительное уточнение; `supersedes` требует доказанной смены редакции; `contradicts` без детерминированной проверки или решения владельца — кандидат, а не установленное противоречие.
- `imports/calls` — синтаксически обоснованные зависимости; динамические вызовы, reflection и runtime wiring помечаются как потенциально неполные. Статический анализ не доказывает фактическое выполнение.
- `implemented_by` не означает `verified`. `verified_by` требует критерия и доказательства с правильным SHA. `illustrated_by` означает демонстрацию, не production-реализацию.
- Наличие одинаковых слов, имён модулей, embeddings или близких описаний создаёт только `inferred/pending` кандидата.
- Переход «нет найденной связи» → «требование отсутствует/не реализовано» запрещён без учёта полноты исходного корпуса и поддержки языка.

## 3. Единица индексации и модель данных

| Сущность | Гранулярность | Обязательные признаки |
|---|---|---|
| Источник | Документ, файл, репозиторий, импортированный артефакт | Стабильный ID, проект, тип, доступ, состояние, роль источника, источник ревизии. |
| Блок документа | Раздел, именованное требование, критерий, абзац, таблица, блок кода; для PDF также страница | ID, родитель, заголовок, путь навигации, диапазон строк или координаты блока на странице, ревизия, хеш извлечения. |
| Компонент кода | Репозиторий, пакет, модуль, класс, функция, маршрут, конфигурационный ключ, тест, схема данных | ID компонента, тип символа, квалифицированное имя, Git SHA, путь и строки, роль `runtime/test/prototype/example/generated`. |
| Задача и критерий | Штатный `task_ref` и идентификатор критерия | Проект, версия формулировки, связь с ТЗ, область кода. |
| Доказательство | Результат теста, CI, ручной проверки или выпуска | ID запуска, критерий, SHA артефакта, результат, дата, источник и область применимости. |
| Ребро | Одна направленная типизированная связь | ID, концы и их ревизии, тип, происхождение, статус разрешения, состояние проверки, один или несколько указателей на источник. |

### 3.1. Идентичность и версии

- Логический ID переживает новую ревизию. Для требования использовать сочетание проекта, ID документа и явного ID требования. `C-10` из двух чек-листов сам по себе не уникален.
- Различать логический ID, ревизию блока и снимок индекса. Для документа в Git хранить SHA и путь, для внешнего источника — ID и версию провайдера или хеш снапшота. Для кода использовать SHA, а незакоммиченную копию маркировать `dirty` с отдельным хешем и привязкой к worktree. Доказательства выпуска принимаются для подтверждённого коммита.
- Для блоков без явного ID использовать устойчивый якорь `document_id + heading_path + block_anchor` и таблицу алиасов. При переименовании или перемещении сопоставлять уникальный явный ID либо однозначное совпадение содержимого и контекста. Коллизии отправлять на разрешение. Смену сигнатуры учитывать в ревизии компонента.
- Состояния редакции `draft/active/superseded/archived` задаются метаданными или решением владельца в рамках проекта. Дата файла помогает сортировке. Применимость определяется редакцией, веткой, версией продукта и областью действия.
- Версионный селектор по умолчанию использует актуальный снимок проекта. Исторический запрос фиксирует `snapshot_id` либо однозначную пару ревизий. Нельзя соединять редакции из разных снимков без явной связи сравнения.

### 3.2. Происхождение и достоверность

Хранить независимые поля. `origin=extracted|inferred|manual` фиксирует способ получения. `resolution=resolved|ambiguous|unresolved` фиксирует качество поиска цели. `review_state=pending|confirmed|rejected` фиксирует проверку человеком или детерминированным валидатором с указанным правилом. В UI метка `AMBIGUOUS` имеет приоритет над `EXTRACTED/INFERRED`, а происхождение остаётся доступным в деталях.

Для семантического извлечения хранить версию модели, схемы и шаблона извлечения. Валидатор проверяет, что оба ID существуют и приводимые цитаты действительно есть в сохранённых фрагментах. Для неоднозначного ребра хранить доступные кандидаты и причины. Оценка модели нужна для ранжирования кандидатов. Повышение до подтверждённой связи требует отдельного доказательства. Отрицательное решение сохраняется для той же версии источника, чтобы повторный проход не создавал ту же карточку.

**Отображение полей существующего графа кода (v2.1, обязательно для G-03).** В `tools/arch_graph.py` поле `evidence_quality='verified'` означает «вызов или импорт разрешён статически», а не «реализация проверена». В этом ТЗ `verified` — только статус реализации по §3.3 (пройденная проверка на SHA). Перенос значения как есть превратил бы весь статический граф в доказательство реализации, поэтому адаптер обязан отображать поля так:

| `arch_graph` | Граф TT-GRAPH-001 |
|---|---|
| `resolution=resolved`, `evidence_quality=verified` | `origin=extracted`, `resolution=resolved`, `review_state=confirmed` (правило: статический разбор, `parser` из provenance). Статус реализации **не** меняется. |
| `resolution=external` | `origin=extracted`, `resolution=resolved`, узел-цель вида `external_module`; в D3/D4 не участвует. |
| `resolution=ambiguous` | `origin=extracted`, `resolution=ambiguous`, кандидаты из обоих концов. |
| `resolution=dynamic_unresolved`, записи `unresolved` с `UNRESOLVED_REASONS` | `resolution=unresolved`, причина сохраняется; находка `unresolved_link`, участок помечается как потенциально неполный (§2.1). |
| `evidence_quality=inferred` | `origin=inferred`, `review_state=pending`. |

Значение `verified` из `arch_graph` не попадает в поле статуса реализации ни в одной проекции, отчёте или пакете агента. Тест G-03 проверяет это явно.

Пример ребра между ТЗ и демонстрацией. Идентификаторы упрощены для иллюстрации.

```json
{
  "schema_version": 1,
  "project": "suptracer",
  "from": "req/dashboard-checklist/C-10@rev1",
  "to": "code/dashboard-concept/remember@commit",
  "type": "illustrated_by",
  "origin": "inferred",
  "resolution": "resolved",
  "review_state": "pending",
  "evidence": ["source/dashboard-checklist@rev1#C-10", "source/concept@commit#remember"],
  "rule_id": "layout-storage-candidate",
  "snapshot_id": "snapshot-example"
}
```

### 3.3. Семантика статуса реализации

| Статус ответа | Условие |
|---|---|
| `verified` | Действующее требование связано с проверкой на выбранном SHA, проверка успешна и подтверждает соответствующий критерий. |
| `linked_unverified` | Найдена подтверждённая привязка к реализации, но актуальная проверка отсутствует, провалена или неприменима. Состояние проверки указать отдельно. |
| `prototype_only` | Найдены только связи с прототипом/демо. |
| `ambiguous` | Есть конкурирующие варианты, цель однозначно не разрешена. |
| `no_evidence` | В доступном снимке цепочка доказательств отсутствует. Вместе со статусом возвращать охват и пробелы индекса. |

Если требование содержит несколько обязательных критериев, статус всего требования `verified` требует успешного доказательства по всем применимым критериям. Статус релиза берётся из действующей релизной политики и связанных артефактов.


### 3.4. Паспорт источника и статусы покрытия

В `sources` и `source_revisions` обязательно хранить: `project_id`, `source_id`, `uri_or_path`, `source_kind`, `format`, `scope`, `branch`, `commit_sha` или `external_revision`, `dirty_state`, `content_hash`, `access_policy_ref`, `include_rule_id`, `parser_id/version`, `processing_status`, `reason_code`, `indexed_blocks`, `last_checked_at`, `snapshot_id`. Для исключённых и недоступных файлов также сохранять безопасную диагностическую запись, не раскрывая пользователям закрытые названия.

Различать состояния `discovered`, `eligible`, `indexed`, `partially_indexed`, `unsupported`, `excluded_by_rule`, `access_denied`, `parse_failed`, `deferred`, `deleted`. Покрытие по форматам считается отдельно: 

```text
eligible_sources = discovered - excluded_by_rule - access_denied - unsupported
source_coverage = indexed_sources / eligible_sources
block_coverage = correctly_parsed_eligible_blocks / all_detected_eligible_blocks
```

Если знаменатель для блока нельзя корректно определить, показатель `block_coverage` помечается `unknown`, а не отображается как 100%. При публикации показывать три значения отдельно: **обнаружено / допущено к индексации / успешно проиндексировано**. Исключения всегда перечислены по группам причин. Метрика точности связей измеряется независимо от охвата.

### 3.5. Находки, кластеры и ревизии базового графа

`Finding` хранит `finding_id`, `kind`, `severity` (как приоритет исследования, не доказанная критичность дефекта), `status`, `scope`, `evidence_refs`, `source_snapshot_id`, `affected_node_ids`, `explanation`, `suggested_review`, `created_at`. Дубликаты findings устраняются по стабильной сигнатуре и области применимости. После обновления находки становятся `open/resolved/stale`, а не исчезают бесследно.

`Cluster` хранит основание группировки: явный пакет/подсистема/путь, либо `algorithmic` с версией алгоритма; `Hub` — ограниченную метрику степени/центральности и объяснение, почему узел стал хабом. Гипотезы и недоступные рёбра не должны искусственно завышать степень. Изменение уровня агрегации не меняет доказательств.

## 4. Сбор, привязка и обновление

### 4.0. ОБЯЗАТЕЛЬНО: первичная реконструкция текущей системы (Initial Graph Bootstrap)

**Триггер:** создание нового графового пространства проекта либо отсутствие валидного исходного снимка. `initial_bootstrap` должен запускаться явно из CLI/UI и может быть предложен при первой конфигурации; запуск, который требует дорогостоящей внешней модели или охватывает внешние источники, требует подтверждённых прав и настроек. Продолжение после сбоя — с безопасного checkpoint; повтор с тем же набором входов идемпотентен.

**Алгоритм на существующих данных:**

1. **Заморозить контекст.** Зафиксировать проект/корни, ветки и worktrees, реальный `HEAD`, состояние незакоммиченных изменений, доступные источники, профиль ACL и исключения. Базовый план по умолчанию относится к текущему worktree и указанным источникам. Другие ветки/архивы индексируются только если явно включены. Никаких утверждений о соответствии произвольным будущим коммитам.
2. **Инвентаризировать всё в разрешённой области.** Обойти дерево с защитой от циклов и симлинков, собрать код, тесты, конфигурации, Markdown, текстовые инструкции, схемы, JSON/YAML, таблицы/скриншоты/PDF по объявленным адаптерам и документы, присоединённые через разрешённые коннекторы. Обнаружение ≠ успешный разбор. `gitignore`, allowlist/denylist, секреты, generated/build и крупные бинарные объекты обрабатываются явными правилами; отчёт объясняет каждый класс исключений.
3. **Опознать структуру и роли.** Определить реальные точки входа, модули, импорты, тестовые пакеты, прототипы, UI, конфигурации, маршруты и компоненты. Найденные имена не объявлять «рабочим продакшен-кодом» без соответствующей роли/доказательств. Дубликаты документов и копии файлов пометить отдельно.
4. **Разметить документацию.** Разбить доступные поддерживаемые документы по блокам, таблицам и критериям, извлечь явные ID/ссылки, применимость и редакции. Для текста поддержать Unicode/кириллицу и проверяемый диапазон. PDF/изображения в `full_corpus` проходят отдельные адаптеры после готовности этапа P3; до этого они перечислены как `deferred/unsupported`, не как проиндексированные.
5. **Разметить код.** Переиспользовать существующий статический граф кода; где точности недостаточно — tree-sitter/парсер языка. Построить стабильные идентификаторы символов и ссылок, зафиксировать динамические зоны, которые статический анализ не покрывает. Создать обратные проекции.
6. **Связать D1 и D2.** Извлечь явные междокументные зависимости, импорты, вызовы и отношения владения/содержания. Неоднозначные цели сохранять с кандидатами; не угадывать.
7. **Связать D3/D4.** По явным `spec_ref`, `task_ref`, ID критериев, именам тестов, коммитам, документации API и другим подтверждаемым указателям построить связи требование ↔ реализация ↔ проверка. Семантическую близость использовать как кандидата, не как итоговое доказательство.
8. **Собрать findings.** Сформировать списки требований без подтверждённых реализаций, компонентов без связанных документов, элементов без тестовых доказательств, конфликтов версий, кандидатов на дубли, хабов и изолированных кластеров. Все выводы сопровождать оговоркой об охвате; отделять отсутствие ребра от доказанного отсутствия реализации.
9. **Проверить и опубликовать.** Сверить ссылочную целостность, типы рёбер, ACL, повторяемость ID, запрет смешивания версий, покрытие и отсутствие вымышленных цитат. Атомарно опубликовать baseline, сохранив прошлый рабочий снимок при ошибке.
10. **Выдать результат.** Сгенерировать `SOURCE_INVENTORY.json`, `GRAPH_BASELINE.json`, `GRAPH_REPORT.md`, `GRAPH_FINDINGS.json`, доступные файлы экспорта и граф в UI; дать CLI/API вход в каждую проекцию. Указать, какие источники оставлены до P3 и какие связи требуют человека.

**Первый запуск без LLM обязателен как деградационный режим:** текстовый индекс, точные ID/ссылки и статический граф кода должны работать без вызова модели и сети. Семантический анализ подключается ограниченно, асинхронно в рамках приложения и только при разрешении политики данных. Нельзя делать доступ к LLM обязательным условием поиска уже индексированных точных ссылок.

**Критерий завершения bootstrap:** опубликован целостный baseline и все четыре направления доступны на данных реального проекта с указанием полноты. Если отдельное направление не имеет подтверждённых рёбер, отображается проверяемое пустое состояние и причины. Выдача «готово» при пустой карте, неуспешном обходе, неучтённых файлах или только демонстрационной фикстуре запрещена.

### 4.1. Постоянный сбор, разрешение связей и обновление

1. **Реестр источников.** Владелец задаёт проект, репозитории, пути, наборы документов, исключения и права. Сначала индексируются рабочие Markdown и текстовые конфигурации. Внешние документы импортируются через разрешённый источник с фиксированной версией. Индекс публикует перечень поддержанных форматов и причину каждого пропуска.
2. **Детерминированное извлечение.** Markdown разбирается структурным парсером с сохранением заголовков, таблиц, чек-листов, ссылок и диапазонов. Длинный раздел дробится по смысловым границам. Для кода использовать существующий статический сканер и его provenance. Tree-sitter подключать по языкам, где штатный разбор не даёт требуемой точности. Совместить ID символов и типы рёбер через адаптер.
3. **Разрешение связей.** Порядок: точный ID или проверенная ссылка → уникальная цель в области проекта/версии → структурные подсказки из `spec_ref`, тестов и конфигураций → семантические кандидаты. Явная ссылка задаёт тот тип связи, который действительно указан. Совпадение токенов даёт кандидата на связь.
4. **PDF и визуальные материалы.** Для PDF извлекать текст по страницам, для сканов применять OCR, сохранять расположение. Для схем и скриншотов разрешать семантический разбор блоков с координатами и признаком использования модели. При спорном OCR показывать страницу и качество. Контент отправлять внешнему провайдеру только если политика конкретного источника это разрешает.
5. **Обновление.** Хеш файла, версия парсера, схемы и параметры извлечения входят в ключ кеша. При изменении пересобирать фрагменты источника и заново разрешать входящие и исходящие рёбра затронутых блоков. При удалении выводить блоки и рёбра из нового снимка и сохранять их в доступной истории. При переезде переносить алиас только при однозначном совпадении.
6. **Триггеры.** Ручной CLI, уведомление о новой версии документа, Git commit/checkout и согласование после pull или обнаружения изменившегося HEAD. Хук ставит идемпотентную фоновую задачу, сообщает о постановке и завершает работу без синхронного обращения к модели. Повторы объединяются по проекту и целевому состоянию входов.
7. **Публикация.** Один писатель на проект. Построение во временном снимке, проверка схемы, ссылочной целостности и разрешений, затем атомарное переключение текущего снимка. Читатель фиксирует один снимок на запрос. При сбое отдавать предыдущий снимок с признаком `stale`, причиной и данными о покрытии. Восстановление индекса из источников штатной командой.

### 4.2. Хранилище

Предлагается локальный SQLite-индекс по проекту. Основные таблицы `sources`, `source_revisions`, `blocks`, `nodes`, `edges`, `edge_evidence`, `snapshots`, `aliases`, `link_reviews`; полнотекстовый индекс по заголовкам, тексту, символам и ID. Использовать FTS5 при наличии и предусмотреть базовый поиск по точным ID/именам в окружении без FTS5. Индекс производный. Оригиналы документов, граф кода и штатные журналы конвейера используются через адаптеры. Решения по связям хранить с журналом и резервной копией отдельно от пересобираемого кеша. Хранилище и зависимости проверить на поддерживаемой Windows и в CI.


### 4.3. Контракт сборки и структура экспорта

Публичный `graph status` должен возвращать как минимум:

```json
{
  "project_id": "suptracer",
  "snapshot_id": "example-immutable-snapshot",
  "baseline_snapshot_id": "example-baseline",
  "state": "ready|partial|stale|building|failed",
  "baseline_stage": "none|text_code_baseline_ready|full_corpus_baseline_ready",
  "git_revision": "<actual HEAD at build time>",
  "inventory": {"discovered": 0, "eligible": 0, "indexed": 0, "excluded": 0,
                "unsupported": 0, "failed": 0, "deferred": 0},
  "graph": {"nodes": 0, "edges": 0, "edge_counts_by_dimension": {}},
  "quality": {"confirmed": 0, "inferred_pending": 0, "ambiguous": 0},
  "report_refs": {"inventory": "SOURCE_INVENTORY.json",
                  "baseline": "GRAPH_BASELINE.json",
                  "findings": "GRAPH_FINDINGS.json",
                  "human_report": "GRAPH_REPORT.md"}
}
```

Числа — **иллюстрация структуры контракта**, не результат анализа SUPtracer. Версии и поля в production должны соответствовать схеме. `state=ready` не означает 100% полноту: доля и причины пропусков показываются всегда. Файлы отчётов располагаются в управляемой внутренней директории проекта, с доступом по ACL; экспорт в публичный HTML разрешён только после редактирования/исключения приватного содержимого.

`GRAPH_REPORT.md` обязан включать следующие разделы: паспорт источников и версии; обнаруженная реальная архитектура; D1/D2/D3/D4 по реальным данным; точные и предположительные связи; основные кластеры; хабы и потенциальные god nodes; требования без подтверждённой реализации; код без документации; тесты и отсутствующие доказательства; конфликты редакций; непокрытые области и причины; изменения с предыдущего снимка; проверяемые рекомендации с ссылками на исходники. Классификация `missing_*` не должна автоматически обозначать дефект продукта.

### 4.4. Контроль изменений и дрейфа

После изменения источников индексатор пересчитывает затронутые блоки и инцидентные рёбра, сохраняя ручные решения, если совпадает версия и семантика источника. Отчёт `graph diff` показывает `added/removed/changed` для источников, узлов, рёбер и findings с уровнем достоверности и причиной пересчёта. Для перемещения файла без изменения логического блока должна сохраняться идентичность там, где это доказано; неразрешённый move не превращается в новую неподтверждённую истину. Состояние релизной проверки привязывается к своему SHA и не переносится на новый коммит автоматически.

Триггеры: ручная команда, commit/checkout/pull, изменения разрешённых документов, плановая сверка ссылок и API hook. Повторные события дедуплицируются. При нагрузке используется очередь с контролем числа параллельных парсеров и расходов LLM. Падение инкрементального прохода не должно повреждать базовый снимок. Для выключенной функции старый механизм SUPtracer продолжает работать.

### 4.5. Контроль полноты без ложных выводов

Каждое утверждение «нет связи / нет реализации / нет теста» сопровождается `coverage_context`, включающим границы сканирования, пропущенные языки/форматы, состав веток, исключения, состояние тестовых артефактов и дату снимка. Отсутствие ссылки не доказывает отсутствие функциональности. При расхождении активных документов система формирует вопрос владельцу и показывает оба фрагмента; не меняет приоритет документа по одной дате файла.

## 5. Поиск и оптимальный маршрут чтения

### 5.1. Контракт поиска

Вход: проект, запрос, необязательные `task_ref`, `from_ref`, `to_ref`, тип сценария, селектор ревизии, ограничения глубины и бюджета. Четыре сценария маршрутизации `lookup`, `implementation`, `impact`, `review`. Запросы на русском и английском, поиск по полным и коротким ID, квалифицированным именам и якорям. Для Markdown и полнотекстового поиска сохранить поддержку дефисов и кириллицы.

Порядок:

1. Ограничить множество источников по правам, проекту и версии. Разрешить точные ID, пути и алиасы. При коллизии дать выбор цели.
2. Если точного входа нет, получить кандидатов полнотекстовым поиском. Учитывать совпадение заголовка, кода требования, полного символа, применимость и привязку к задаче. Семантическое переранжирование подключать опционально к малому набору кандидатов.
3. Пройти граф от нескольких лучших якорей. По умолчанию максимум 4 ребра, 300 посещённых узлов, до 3 уникальных маршрутов. По запросу влияния смотреть входящие рёбра D2 и обратные D3. По запросу реализации искать цепочку от действующего требования к рабочему компоненту и доказательству.
4. Для каждого сценария разрешить набор типов рёбер. Поиск пути выполнять алгоритмом Дейкстры с неотрицательной стоимостью. Состояние поиска включает узел, глубину и, для доказательного запроса, фазу прохождения цепочки. Возвращать несколько альтернатив с ограниченным бюджетом обхода, исключая циклы в одном пути.
5. Собрать минимальный набор фрагментов, достаточный для ответа. Начать с нужного абзаца или символа, раскрывать родительский контекст по запросу. Убрать дубли по источнику, диапазону и хешу. Сохранить порядок чтения: требование → реализация → проверка. Указать причины пропуска, если достигнут лимит.

### 5.2. Стоимость пути

Начальные коэффициенты настраиваются и версионируются. Стоимость маршрута складывается из штрафа за низкую релевантность входного блока и стоимости каждого шага:

```text
edge_cost = 1 + relation_penalty + provenance_penalty
          + hub_penalty + reading_penalty
```

| Фактор | Начальное значение |
|---|---|
| Тип отношения | 0 для целевого типа, 1 для вспомогательной связи, 3 для общего перехода через контейнер. |
| Происхождение | 0 для подтверждённой или явно разрешённой связи, 2 для непроверенной гипотезы в режиме исследования. Неоднозначные связи выносятся в кандидаты. |
| Хаб | От 0 до 2 после порога исходящей степени. Считать только доступные узлы. Сбрасывать штраф для точного якоря по ID. |
| Объём чтения | `min(3, estimated_fragment_tokens / 400)` для очередного фрагмента. |

Историческая ревизия участвует в актуальном маршруте только по разрешённому переходу. Устаревшие, скрытые, отклонённые и неоднозначные связи исключаются из доказательной цепочки. При равной стоимости выбирать более релевантный путь и затем стабильный ID. Объяснение сообщает, почему путь выбран и какие ссылки требуют подтверждения. Для первого выпуска допустима оценка токенов с запасом. При наличии токенизатора модели использовать точный подсчёт.

### 5.3. Выход и чтение

Ответ содержит `snapshot_id`, ревизии, `coverage`, `status`, `paths[]`, `excerpts[]`, `alternatives[]`, `truncated`, `fallback_used`. Для шага указать тип ребра, происхождение, верификацию, стоимость и ссылки. У фрагмента есть заголовок, контекст, версия, точный диапазон и действие «Открыть источник». Поиск без пути возвращает точечные находки и объясняет пробел. Индексированная ссылка при открытии сверяется с выбранной ревизией. При смене редакции можно открыть сохранённый фрагмент или новую редакцию с явным указанием различия.


### 5.4. Особые маршруты по исходной структуре

Реализовать сценарии (после начального построения, а не только на новых событиях):

| Запрос | Маршрут | Что возвращать |
|---|---|---|
| «Покажи архитектуру этого проекта» | project → domain → module → symbol | Свернутый текущий граф, точки входа, роли и покрытие |
| «Какие требования не имеют подтверждённого кода?» | active requirement → D3 → runtime | Список с `no_evidence/ambiguous/prototype_only`, охват источников и кандидаты |
| «Почему существует этот метод?» | code symbol → D4 → requirement → task | Подтверждённый документ или явно помеченная гипотеза |
| «Что сломается при изменении функции?» | symbol → reverse D2 → reverse D3 → tests | Пути влияния с ограничениями статического анализа |
| «Какие документы относятся к блоку разработки?» | module/task → D4/D3 → D1 | Минимальный пакет фрагментов, редакции, авторитетность |
| «Что стало иначе после коммита?» | snapshot A ↔ snapshot B | Новые и изменённые блоки, связи, критические разрывы и доказательства |

Для планирования чтения после точного поиска использовать путь минимальной стоимости. Не заменять по умолчанию точный поиск большим LLM-резюме: цитируемые фрагменты и маршрут должны оставаться первичными результатами.

### 6.1. Интерфейс

- **Поиск.** Поле запроса, переключатель сценария, фильтры проекта/версии/типа. Результат показывает первый точный фрагмент, а путь раскрывается по кнопке. Показывать охват индекса и дату обновления.
- **Карточка задачи.** Блок «Связанные требования и проверки» с четырьмя направлениями, группировкой по критериям и ссылкой на испытание. При отсутствии теста выводить «Проверка отсутствует в доступных данных».
- **Карта влияния.** Раздельные списки компонентов, требований и проверок. По каждому элементу доступно обоснование. Для больших графов загружать ограниченное окружение выбранного узла.
- **Отчёт.** Кластеры по реальным связям с объяснением включения, хабы с метрикой степени, конфликты, пробелы и предлагаемые вопросы. Начать с групп по доменам и компонентам; алгоритмическую кластеризацию добавлять после измерения качества.
- **Режимы.** В live-режиме доступны поиск и owner-решения. В автономный HTML включать только явно разрешённый снимок просмотра, если такой экспорт включён. Клавиатурная навигация, возврат фокуса, понятный текстовый режим и пустые/частичные состояния обязательны.


### 6.2. Команды первоначальной сборки и управление проектом

Предлагаемый CLI (точная форма согласовывается с фактическими возможностями `tools/pm.py` на текущем HEAD):

```text
pm.py graph discover --project <id> --dry-run
pm.py graph bootstrap --project <id> --profile text-code
pm.py graph bootstrap --project <id> --profile full-corpus
pm.py graph status --project <id>
pm.py graph report --project <id> --format md
pm.py graph explore --project <id> --dimension D1|D2|D3|D4
pm.py graph search --project <id> --query "..."
pm.py graph impact --project <id> --ref <node-id>
pm.py graph diff --project <id> --from <snapshot> --to <snapshot>
pm.py graph rebuild --project <id> --verify-equivalence
```

`discover --dry-run` формирует инвентарь и анализ ACL без создания/переключения базового снимка. `bootstrap` публикует целостный снимок только после валидаторов. `report` по умолчанию не раскрывает больше данных, чем разрешено вызывающему. В UI первая настройка содержит мастер «Построить граф существующего проекта», видимый перечень источников/исключений, статус этапов, охват и ссылку на отчёт.

Дополнительные API (имена примерные): `POST /api/graph/discover`, `POST /api/graph/bootstrap`, `GET /api/graph/inventory`, `GET /api/graph/report`, `GET /api/graph/explore`, `POST /api/graph/diff`. Команды записи ограничить owner-правами и идемпотентностью; права на чтение применить и к агрегатам/экспорту. Процессы длительной индексации возвращают `job_id` и статус задачи в системе; HTTP-обработчик не должен ждать полного прохода или вызывать LLM синхронно.

### 6.3. Технические границы интеграции

- Не дублировать существующий статический граф кода — работать через адаптер и унифицированные типы узлов.
- Одна модель трассировки на систему: трассировка TT-ARCH-001 §4A («процесс → шаг → функция/модуль») и D3/D4 этого ТЗ — один слой связей. Расхождение типов связей устраняется таблицей соответствия в G-02, а не параллельным хранилищем.
- Не дублировать разбор Markdown и привязку коммитов к задачам: `mdparse.py` и `tree.py` — штатные источники (см. таблицу выше).
- Не связывать функциональность графа с обязательным выпуском Dashboard 3.0: должен существовать рабочий CLI и доступный текущему интерфейсу API.
- Граф не является источником истины для смены статуса задачи, слияния веток или выпуска; проверки и блокировки остаются в штатном конвейере.
- Интеграция с LLM (включая локальную модель) получает небольшие фрагменты с provenance, строгим budget и явно переданными разрешениями. При недостаточности контекста запрос расширяется точечно.
- Новые файлы/адаптеры привязать к существующей структуре после ревизии реального `HEAD`. Указанные в исходном ТЗ `tools/arch_static.py`, `tools/arch_graph.py`, `tools/workflow.py` и другие — **кандидаты**, проверяемые при P0, не гарантия их актуальной сигнатуры.

## 7. Права и эксплуатация

- Применять область доступа до полнотекстового подбора, обхода, расчёта степени хабов и агрегации отчётов. Проверять права на оба конца ребра, доказательство и текст фрагмента. По закрытым источникам не раскрывать имена, счётчики и наличие кандидатов.
- Путь к файлу нормализовать и сверять с разрешённым корнем после разрешения символических ссылок. Секреты, окружение, личные журналы и генерируемые копии исключать по настройкам и правилам проекта. Не включать исходный приватный текст в логи и клиентский кеш.
- Документы и код обрабатывать как данные. HTML экранировать, ссылки ограничивать разрешёнными схемами, команды из документов не исполнять. Модель извлечения получает минимальный фрагмент без доступа к операциям записи. Её ответ проходит JSON-схему и проверку ссылок на исходные данные.
- По каждой сборке сохранять охват форматов, число обработанных/пропущенных источников, время, объём индекса, число устаревших рёбер и расход модели. Ошибка отдельного источника даёт `partial`; результат показывает причину.
- Версия схемы и миграции обязательны. Проверить откат индекса к предыдущему совместимому снимку и восстановление ручных решений после пересборки. Граф влияет на подсказки и подготовку контекста. Переходы статусов выполняются штатными правилами TaskTreker, включая прекращение набора задач в проекте до вливания всего текущего состава спринта в `main`.

## 9. Приёмка и метрики

Перед испытанием зафиксировать ревизию кода, версии документов, железо, парсеры, параметры поиска и модель. Эталон — минимум 40 вопросов, включая 8 на каждое из четырёх направлений и 8 на конфликты/двусмысленность/отсутствие ответа. Разметить правильные фрагменты до настройки коэффициентов. Не менее 25% вопросов оставить для независимой финальной проверки. Для пилота по MiMo использовать шесть существующих сценариев разработки с одинаковыми моделью, бюджетом и условиями сравнения.

- [ ] **AC-01. Гранулярность.** Требование, пункт таблицы, тест и символ открываются на точном диапазоне. Одинаковый короткий ID в двух документах даёт корректный выбор версии и цели.
- [ ] **AC-02. Четыре направления.** Фикстура покрывает D1–D4. Прямой и обратный ход используют единый ID ребра. Задача и тест доступны через связанные сущности.
- [ ] **AC-03. Достоверность.** Для C‑10 доступна ссылка на демо-хранение раскладки. Статус `verified` не появляется без версии, отката и проверки в рабочем UI. Смена SHA переводит прежнюю проверку в историческую.
- [ ] **AC-04. Поиск.** Точный применимый источник для валидного ID находится первым. `Recall@3 ≥ 90%` по эталонным запросам с ответом. В отчёте указать знаменатель, исключения и разрез по направлениям.
- [ ] **AC-05. Объём чтения.** На эталоне медиана токенов прочитанных фрагментов до правильного ответа минимум на 25% ниже исходного поиска при сохранении точности ответов. Замер включает раскрытые фрагменты и повторы.
- [ ] **AC-06. Маршрут.** В фикстуре короткая цепочка через демо и более длинная подтверждённая цепочка ранжируются по цели. Статус реализации опирается на подтверждённую цепочку. Достигнутые ограничения отражаются в выдаче.
- [ ] **AC-07. Ревизии.** Активная версия находится по умолчанию. Явно выбранная историческая редакция восстанавливает старые диапазоны. Конфликт двух действующих требований показывается с двумя источниками.
- [ ] **AC-08. Инкрементальность.** Неизменённый источник даёт попадание в кеш. Переименование, удаление, смена парсера и изменение цели пересчитывают затронутые связи. Снимок после обновления эквивалентен чистой пересборке по нормализованным узлам и рёбрам.
- [ ] **AC-09. Надёжность.** Принудительное завершение при построении сохраняет доступ к последнему целостному снимку. Два одновременных триггера не создают две публикации для одинакового входа. При отказе семантики точный поиск остаётся доступен.
- [ ] **AC-10. Безопасность.** Проверки ACL, owner-write, обхода пути, XSS и инструкций внутри документов проходят. Закрытый источник не виден в путях, отчётах, экспорте и агентском пакете.
- [ ] **AC-11. Задержка.** Цель p95 для локального поиска с прогретым индексом ≤500 мс на 50 тыс. блоков и 200 тыс. рёбер при настройках по умолчанию, без LLM. Холодный старт и семантический режим измеряются отдельно. Зафиксировать измеритель, железо и распределение запросов.
- [ ] **AC-12. Пакет агента.** Соблюдён общий бюджет, есть ссылки на запрос и источники. На шести сценариях число пройденных критериев не падает, возвраты и выходы за scope не растут; входные токены, время и стоимость измерены по обоим вариантам.
- [ ] **AC-13. Рабочий UI.** Владелец открывает источник и доказательство из карточки задачи. Пустое, частичное и устаревшее состояния различимы. Навигация через клавиатуру работает.
- [ ] **AC-14. Совместимость.** Пройдены целевые Python-тесты, браузерные проверки и штатный `pm.py check`. При выключенной функции (флаг `graph_4d_enabled` выключен, это значение по умолчанию) исходные пакеты задач, рабочая доска и переходы конвейера работают по прежнему контракту; тест сравнивает `workflow.packet()` с флагом и без него.
- [ ] **AC-15. Воспроизводимость.** Для каждого критерия сохранены сценарий, ревизии, команда или шаги, фактический результат и ссылка на доказательство. Сборка и обновление повторены на целевом окружении.


### 9.1. Новые обязательные критерии приёмки первоначальной реконструкции (v2.0)

- [ ] **B-01. Реальные существующие данные.** В заранее подготовленном репозитории с файлами, созданными до установки функции, первая сборка индексирует текущий код, документы, конфигурации и тесты без добавления фиктивных новых файлов. Подтверждение: снимок, список входов, числа узлов/рёбер и открываемые оригиналы.
- [ ] **B-02. Полный паспорт источников.** Все файлы в заданных разрешённых корнях учитываются как обработанные, отложенные, исключённые, неподдерживаемые, недоступные или ошибочные; проверка выборочной сверкой списка файлов и manifest. Для каждого пропуска указана причина, состояние и формат.
- [ ] **B-03. Четыре графа на первом снимке.** До первого последующего коммита доступны проекции D1/D2/D3/D4 и обратные переходы; для каждой проверены хотя бы два реальных источника или честное пустое состояние с объяснённым отсутствием найденных отношений.
- [ ] **B-04. Уровень блока.** Из графа требование/абзац/критерий открывается по точному месту; компонент — по файлу, символу и строкам. Агрегация в кластер не ломает drill-down и не теряет provenance.
- [ ] **B-05. Реальный GRAPH_REPORT.** Отчёт содержит измеренные источники, роли модулей, текущие кластеры, god nodes, статусы связей, разрывы между требованиями и кодом, неразрешённые цели, ограничения покрытия; примеры перепроверены вручную. Нельзя подменять отчёт шаблоном с выдуманными показателями.
- [ ] **B-06. Корректные разрывы.** Известная фикстура с реализованным, отсутствующим, прототипным и непротестированным требованием различается статусами. Недоступный или неподдержанный файл приводит к `index_gap/unknown`, а не к безусловному «не реализовано».
- [ ] **B-07. Ревизии и источник истины.** Базовый снимок сохраняет SHA/dirty/version. После изменения и удаления файлов `graph diff` показывает обоснованные дельты, ранее подтверждённые проверки не переносятся на новый SHA, старый снимок остаётся доступен.
- [ ] **B-08. Повторяемость.** Повтор bootstrap на том же наборе входов не создаёт лишних узлов/рёбер; нормализованные результаты совпадают. `clean_rebuild` и `incremental_sync` приводят к эквивалентному актуальному состоянию, кроме разрешённых метаданных запуска.
- [ ] **B-09. Доступность без LLM.** При отключённой модели проходят discovery, базовый bootstrap, точный поиск, статические связи и чтение ранее построенного графа. Расходы и вызовы модели в этом режиме равны нулю.
- [ ] **B-10. UI текущей системы.** Из существующего интерфейса и/или отдельного Graph Explorer пользователь видит обзор, раскрывает кластер до документа/символа, включает фильтры и понимает разницу `confirmed/inferred/ambiguous`. Крупный граф не блокирует страницу и не скрывает данные молча.
- [ ] **B-11. Безопасный первичный обход.** Фикстуры с симлинками, закрытыми документами, секретами, HTML-инъекцией и вредоносной инструкцией внутри файла не приводят к чтению/выдаче сверх прав, выполнению инструкций или утечке в отчётах и экспортируемых снимках.
- [ ] **B-12. Готовность этапов.** В P1 корректно выдано `text_code_baseline_ready` с видимыми отложенными PDF/сканами. После P3 отдельный прогон создаёт расширенный снимок; `full_corpus_baseline_ready` не устанавливается при незадекларированных пропусках включённых поддерживаемых источников.

### 9.2. Измерения и критерии выхода

Обязательный отчёт о приёмке показывает: `discovered/eligible/indexed/deferred/failed/excluded` по форматам; распределение `confirmed/inferred/ambiguous`; число найденных точных ссылок; долю ответов с воспроизводимым путём; `Recall@3`; объём чтения и токены; p50/p95 выдачи; время/память/стоимость полного и инкрементального построения; число findings по категориям; число и причины ложноположительных предложений; совпадение full rebuild и incremental; влияние на шесть сценариев агента.

**Целевые пороги, унаследованные из v1.0:** `Recall@3 ≥ 90%` на размеченных запросах с ответом, медиана объёма чтения минимум на 25% ниже базового поиска при сохранённой точности, p95 локального поиска ≤500 мс при 50 тыс. блоков/200 тыс. рёбер без LLM на зафиксированном оборудовании. Это **цели испытаний**, а не измеренные характеристики. Отдельно фиксируются абсолютные показатели охвата: процент не назначается задним числом без реального инвентаря. «100% охват» допустим только применительно к *eligible* источникам данного профиля, не ко всем существующим в мире данным проекта.

**Выходной контроль:** `P0 → P0.1 → P1 → P1.1 → P2 → P3 → P3.1 → P4`; следующий этап не устраняет дефекты предыдущего задним числом. Каждый шаг должен сохранить команды воспроизведения, реальные результаты, логические IDs и доказательства тестов.

## 10. Результат разработки

Готовая поставка включает **работающий индексатор уже существующей базы**, команду `graph bootstrap`, первоначальную карту D1–D4, `SOURCE_INVENTORY.json`, `GRAPH_BASELINE.json`, `GRAPH_REPORT.md`, `GRAPH_FINDINGS.json`, интерактивный Graph Explorer, команды эксплуатации и сравнения снимков, штатный API и UI, версию схемы и справочник типов связей, конфигурацию пилотного проекта, журнал проверок связей и инструкцию обновления/восстановления. Приёмка оформляется таблицей «требование → код → проверка → результат → SHA». Порог с недостаточным объёмом испытаний отмечается как измеренный на ограниченной выборке с указанием её размера.
