# CLAUDE.md — регламент ведения TaskTreker

Это система проектного управления портфелем. Здесь описано, **как её обновлять**.
Читать целиком перед любым изменением данных.

## Что это

Панель по всем проектам пользователя: что сделано, готовность, затраты токенов, бэклог
с размерами, ИБ, архитектура, мощности, LLM, цели, оценка и конкуренты.
Источник истины — файлы в `data/`, дашборд собирается из них.

## Правило номер один

**Автоматические данные не правятся руками, ручные данные не перезаписываются скриптом.**

| Файл | Кто ведёт | Что внутри |
| --- | --- | --- |
| `data/projects.json` | **Клод, вручную** | Цели, что сделано, готовность, бэклог, ИБ, архитектура, мощности, LLM, оценка |
| `data/competitors.json` | **Клод, вручную** (по результатам веб-поиска) | Конкуренты, преимущества, угрозы, вердикт |
| `data/comments.json` | **Пользователь** через `pm.py comment`, разбирает Клод | Комментарии → бэклог и техдолг |
| `data/usage.json` | `collect_usage.py` | Факт по токенам и деньгам из журналов сессий |
| `data/repos.json` | `collect_repos.py` | Git, объём кода, тесты, TODO, гигиена ИБ, подозрение на секреты |
| `data/estimates.json` | `estimate.py` | Оценка оставшихся задач в токенах и деньгах |
| `data/snapshots/*.json` | `pm.py snapshot` | История для трендов — **никогда не удалять и не править** |
| `dashboard.html` | `build_dashboard.py` | Сборка. Правки тут затираются при следующем `refresh` |

## Порядок обновления (выполнять именно так)

### 1. Разобрать комментарии — ПЕРВЫМ ДЕЛОМ

```bash
py tools/pm.py comments
```

Каждый комментарий со `status: "new"` — это задача, которую пользователь поставил
и ждёт в бэклоге. По каждому:

1. Понять, это бэклог, техдолг, баг или вопрос.
2. Добавить задачу в `backlog` нужного проекта в `projects.json` — с `id`, `title`,
   `size` (S/M/L/XL), `priority`, `status`, и `why` (почему это важно — своими словами,
   не цитатой комментария).
3. В `comments.json` поставить `"status": "processed"` и `"moved_to": "<проект>/<id задачи>"`.
4. **Ничего не удалять.** Разобранный комментарий остаётся в файле как след решения.

Если комментарий непонятен — не выдумывать. Оставить `new` и спросить пользователя.

### 2. Пересобрать факты

```bash
py tools/pm.py refresh
```

Запускает по очереди: токены → репозитории → оценки → дашборд → снимок.
`--fast` пропускает сканирование репозиториев (на крупном репозитории это минуты) —
годится, когда менялись только тексты.

### 3. Сверить ручные данные с фактами

Собранные цифры часто противоречат тому, что записано в `projects.json`. **Факт побеждает.**
Что проверять каждый раз:

- **Коммиты выросли, а `done` не изменился** → прочитать `git log` за период и дописать
  сделанное. Это главный источник устаревания.
- **Появились `secrets_suspect` вне `.claude/worktrees`** → проверить глазами, это
  настоящий секрет или имя переменной. Настоящий — в `security.open_critical` и в бэклог.
- **`dirty_files` > 0 держится несколько обновлений** → незакоммиченная работа, спросить.
- **Пропал git или упало число тестов** → это регресс, вынести в тревоги.
- **Готовность** пересматривать только при доказательстве: закрытая фаза, пройденный гейт,
  новый раздел ТЗ. Не двигать проценты «на глаз» — в `readiness.basis` должно быть
  написано, на чём основана цифра.

### 4. Обновить конкурентов — при крупном пересмотре

Не каждый раз, а когда проект заметно сдвинулся или прошло 2–3 месяца.
Веб-поиск, затем правка `competitors.json` и поля `researched`.

## Как писать в `projects.json`

- **`done`** — только то, что реально работает и проверяемо. Не «начата работа над X».
- **`readiness`** — пять цифр, и `basis` обязателен. Пустой `basis` = цифра выдумана.
- **`backlog`** — `size` влияет на оценку затрат: S=1, M=3, L=8, XL=20 коммитов
  (`size_calibration`). Ставить честно: завышенный размер раздувает прогноз по всему портфелю.
- **`security`** — разделять открытое и закрытое. Закрытая находка переезжает
  в `closed_critical`, а не удаляется: история важна.
- **`assessment`** — оценка должна быть полезной, а не вежливой. Если проект стоит закрыть,
  так и писать. Пользователь просил оценку, а не одобрение.
- **Языки**: всё по-русски. Технические идентификаторы (коды требований и находок, имена
  файлов, названия веток) — как есть, не переводить.

## Чего не делать

- Не писать в `usage.json`, `repos.json`, `estimates.json` — затрётся.
- Не удалять снимки из `data/snapshots/` — это единственная история трендов.
- Не править `dashboard.html` — пересобирается.
- Не повышать готовность без доказательства в `basis`.
- Не выбрасывать разобранные комментарии.
- Не публиковать репозиторий без ревизии: в `data/` лежат пути, оценки и находки ИБ.

## Ветки

`разработка` → `тестирование` → `main`, движение только в эту сторону.

- **Вся работа — в `разработка`.** Прямых коммитов в `тестирование` и `main` не делать,
  туда только сливать из предыдущей ветки через `--no-ff`.
- **Перед любым слиянием — `py tools/pm.py check`.** Код возврата 1 означает «не сливать»:
  проверки ловят пустой `readiness.basis`, задачи бэклога без размера, нерасписанный
  по проектам расход токенов, расхождение бэклога с оценкой, ключи в данных и несобираемый
  дашборд. Провал — это всегда настоящая проблема данных, а не придирка; чинить, а не обходить.
- Еженедельный разбор и ежедневная автозадача работают в той ветке, которая выгружена
  в рабочем дереве. Держи выгруженной `разработка`.

## Автоматизация — что уже работает само

- **Ежедневно 09:00** — задача планировщика Windows `TaskTreker\Обновление портфеля`
  запускает `ops/refresh.cmd` → `pm.py refresh`. Обновляет **только генерируемые** файлы.
  Лог: `ops/logs/refresh.log`.
- **Понедельник 10:00** — запланированная задача Клода `tasktreker-weekly-review`
  (`~/.claude/scheduled-tasks/tasktreker-weekly-review/SKILL.md`): разбор комментариев,
  сверка записанного с фактами, отчёт. Она выполняет ровно этот регламент.

Поэтому при ручном обновлении не удивляйся свежим `usage.json` и `repos.json` — их уже
обновила автозадача. Твоя работа начинается с шага 1 (комментарии) и главная её часть —
шаг 3 (сверка). Если правишь регламент ниже, **поправь и текст запланированной задачи** —
иначе еженедельный разбор будет работать по старым правилам.

## Команды

```bash
py tools/pm.py init             # первый запуск: примеры -> рабочие файлы
py tools/pm.py refresh          # всё: токены, репозитории, оценки, дашборд, снимок
py tools/pm.py refresh --fast   # без пересканирования репозиториев
py tools/pm.py status           # сводка по портфелю
py tools/pm.py status <проект>  # подробно по проекту
py tools/pm.py comments         # список комментариев
py tools/pm.py comment <проект> "текст" --kind техдолг
py tools/pm.py check            # гейт перед слиянием в тестирование и main
py tools/pm.py snapshot         # снимок для трендов
py tools/pm.py open             # открыть дашборд
```

## Как считаются деньги

Эквивалент по прайсу Anthropic API, а не счёт подписки: Opus 5 и Opus 4.8 — $5/$25 за 1M
(вход/выход), Sonnet 5 — $2/$10, Fable 5 — $10/$50. Запись кеша 1.25× от входа при TTL 5 минут
и 2× при 1 часе, чтение кеша 0.1× (Fable 5.1 — 0.025×). Прайс лежит в `tools/pricing.py`
и **проверяется через skill `claude-api` при каждом крупном обновлении** — он меняется.

Журнал сессий пишет каждый ответ ассистента дважды, поэтому сборщик дедуплицирует
по `requestId`. Без этого расход завышается вдвое.
