### Решения

- **Хранилище.** Снимок пишется атомарно в `data/arch/inventory.json`. Это личный каталог вне git, как
  `learning/` и `security/`. ТЗ §5.3 советует SQLite, но там же сказано: если в системе уже есть согласованный
  слой хранения, расширять его. В системе такой слой — JSON и `taskstate.save_json`. Переход на SQLite стоит
  делать, когда понадобится история снимков (NET-FR-16, P1).
- **Compose.** Разбирается через `yaml.safe_load`, без `docker compose config`: эта команда подставляет секреты
  из `.env`. Поля `environment`, `env_file`, `secrets` и `command` не читаются. Порт с переменной не подставляется:
  в отчёт идёт имя переменной, порт хоста остаётся неизвестным.
- **Docker inspect.** Читается только allowlist полей: Id, Name, State.Status, Image, ExposedPorts,
  HostConfig.PortBindings, NetworkSettings.Ports и метки `com.docker.compose.*`. Env, Cmd, Entrypoint и Mounts
  не читаются.
- **Проект контейнера.** Определяется только по метке `com.docker.compose.project.working_dir` через
  `project_routes`. Похожее имя доказательством не считается.
- **Владелец сокета.** Это процесс с известным временем создания, созданный не позже сокета. Без времени
  создания идентичность не доказана: в объекте остаётся только подсказка `owner_pid`.
- **Пересечения.** Два сокета, которые наблюдаются одновременно, тем самым доказали совместимость, конфликта нет.
  Объявленные порты разных проектов дают `conflict_suspected`. `conflict_confirmed` без доказательства
  несовместимости не ставится.
- **Права.** Владелец видит всё, кроме `execute_deployment` и `run_scan_remote`: их в MVP нет ни у кого.
  Агент проекта видит только объекты, у которых проект доказан. Хостовые сокеты и резервации ОС без проекта
  видит только владелец. Чужой объект и несуществующий дают один и тот же ответ 404.

## TT-134 · Статический граф Python: модули, символы, импорты, вызовы, маршруты

Ветка `ai/claude/tt-134`. Модули и их тесты:

| Модуль | Назначение | Тест |
| --- | --- | --- |
| `tools/arch_graph.py` | Схема слоя кода: виды узлов, типы связей и допустимые концы, provenance, версии | `test_arch_static.Schema`, `Versions` |
| `tools/arch_static.py` | Коллектор AST только для чтения: охват, разбор, импорты, вызовы, маршруты, CLI, задания, проект | `test_arch_static` (18) |

Fixture лежат в `tests/fixtures/arch/code/`:

- пакет `app`: ядро, маршруты, динамические места, CLI;
- одноимённая функция в `other/pkg`;
- `canary.py` и `setup.py`: при исполнении они оставили бы метку.

Исключаемые каталоги, ссылки, файл с ошибкой синтаксиса и большой файл тест создаёт во временной копии.

### Решения

- **Только AST.** Файл читается байтами и разбирается `ast.parse`. Модули проекта не импортируются,
  `setup.py` и postinstall не запускаются, зависимости не ставятся. Git опрашивается командами только чтения
  (`rev-parse`, `status`) через `job_runner`.
- **Импорт ≠ вызов ≠ сеть.** `imports` — только между модулями, `calls_static` — от кода к коду. Типов
  сетевых и runtime-связей (`network_connects`, `calls_observed`, `deployed_as` и др.) этот слой не строит:
  `validate_edge` их отклоняет. URL в аргументе `requests.get` не становится ребром.
- **Вызов разрешается только по доказательству.** Подходят:
  - своя функция модуля;
  - функция однозначно импортированного внутреннего модуля;
  - метод того же класса через `self` или `cls`;
  - создание экземпляра своего класса.

  Остальные вызовы идут в счётчики `calls_external` и `calls_unknown_target`, связи не появляется.
- **Динамика — отдельной записью `unresolved`** с файлом, строкой и причиной. Сюда попадают:
  - `getattr` с вычисляемым именем и вызов результата `getattr`;
  - `importlib.import_module` и `__import__`;
  - `eval`, `exec`, `compile`;
  - лямбда в таблице команд;
  - `target` фонового задания без известной функции.
- **Неоднозначный импорт не выбирается.** Пример: `import core`, а в репозитории два модуля `core`. Это даёт
  `ambiguous` к обоим с качеством `inferred`, и имя не связывается: вызовы через него не разрешаются. Сторонний
  пакет — `external` с качеством `inferred`: установку анализ не проверял. Модуль стандартной библиотеки — `verified`.
- **Устойчивые ID.** Узел — хеш (вид, repo_id, полное имя), связь — хеш (тип, начало, конец). Номера строк
  и SHA в ID не входят. Все места одной связи лежат в `locations`: repo_id, commit_sha, файл, строка, столбец
  и версия разборщика. Маршрут ключуется модулем: одинаковый путь двух приложений даёт два маршрута.
- **Маршруты.** Ищутся декораторы `route/get/post/…` с путём-константой. В `do_GET`/`do_POST` обработчика
  `http.server` ищутся ветки `if path == "/x"`, `path in (…)`, `path.startswith("/x")`. Вид обработчика:
  - `function` — ветка из одного вызова метода, который больше нигде не вызывается;
  - `inline` — маршрут остаётся за `do_X`. Так и с общим ответчиком вроде `send_json`: обработчиком он не считается;
  - `fallthrough` — путь есть только в списке `if path not in (…)`.
- **CLI.** Таблица команд верхнего уровня (`COMMANDS = {"имя": функция}`) и `add_parser` + `set_defaults(func=…)`.
- **Проект и runtime.** Проект репозитория определяется по пути из реестра (`project_routes`):
  - один владелец — `confirmed_path`;
  - два владельца — `ambiguous`;
  - только похожее имя — `unassigned`.

  Узел кода связывается с объектом runtime только по ручному подтверждению (`link_runtime`), не по имени и не по порту.
- **Версии.** Граф хранит `version_ref`: commit_sha, ветку, признак незакоммиченных правок. Состояние
  развёртывания — отдельное поле `deployment`:
  - `deployed_verified` — только при том же полном SHA артефакта и чистом дереве;
  - `mismatch` — SHA другой, хранятся обе версии;
  - `not_verified` — во всех остальных случаях.
- **Охват.** Только внутри корня, через realpath; ссылки отклоняются с причиной. Пропускаются скрытые
  каталоги, `.venv`, `node_modules`, `dist`, `build`, `tmp`, `*.egg-info`, `*.worktrees` и рабочие копии Git.
  Лимиты: 5000 файлов, 1 МБ на файл, 120 с. Превышение отмечается в coverage как `truncated` и `refused`.
- **Хранение.** `arch_static.py --save` пишет `data/arch/code/<repo>.json`, вне git, как инвентарь.

## TT-135 · Бизнес-процессы и трассировка шаг → код → сервис → порт

Ветка `ai/claude/tt-135`. Модуль `tools/arch_process.py`, тест `tests/test_arch_process.py` (17).

Fixture:

- синтетический процесс заказа (в тесте) на графе кода `tests/fixtures/arch/code`: исключающий
  и параллельный шлюзы, цикл ожидания оплаты, таймаут, асинхронное сообщение, компенсация, ручной шаг;
- реальный процесс TaskTreker — конвейер задачи из `docs/КОНВЕЙЕР.md` на ревизии `8854064`
  (`tests/fixtures/arch/process/tasktreker_pipeline.json`), на графе кода самого репозитория.

### Решения

- **Схема.** `BusinessProcess` с шагами и потоками. ID устойчивые: процесс — (проект, ключ), шаг —
  (процесс, ключ шага), поток — (процесс, начало, конец, вид). Версия — отдельное поле и не меняет ID.
  `validate` собирает все ошибки сразу:
  - поток ссылается на несуществующий шаг;
  - нет начала или конца;
  - шаг недостижим от начала;
  - шлюз не ветвит и не сводит;
  - условный поток без условия;
  - асинхронное сообщение не от шага отправки;
  - ссылка на требование не в формате BR/FR/NFR/UC/TC.
- **Пути.** `paths` перечисляет все альтернативы от начала до конца и не сводит их в один «правильный» путь.
  Шаг посещается не больше двух раз за путь, поэтому возврат на доработку проходится один раз и поиск конечен.
  Параллельный шлюз отмечается списком ветвей. Лимит — 64 пути, превышение даёт `truncated`.
- **Согласование.** Предложение ИИ — всегда `proposed`. Утверждает только владелец:
  - документированный источник — при наличии ссылки и ревизии;
  - ИИ или владелец без документа — с записанным доказательством.

  Утверждённое не входит в реестр напрямую: `approve` — отдельное действие.
- **Реестр.** `data/arch/processes.json`, вне git. Версии не перезаписываются: та же версия с другим содержанием
  отклоняется, понижение версии — тоже, история читается целиком. Права:
  - агент видит процессы только своего проекта и может только предложить;
  - подтверждённую привязку шага ставит только владелец;
  - чужой процесс и несуществующий дают одну и ту же ошибку.
- **Привязка шага** — к маршруту, команде, функции, классу, заданию или модулю графа кода, с источником
  и ревизией. Подтверждённая — `doc`/`test` с ревизией или `owner`; `inferred` и `llm` — нет. Ручному шагу
  привязка не назначается вовсе.
- **Трассировка.** Цепочка `realizes_process_step` (logical) → `handles_route`/`handles_command` (call) →
  `deployed_as` (deployment) → `exposes_endpoint` (network), каждый переход со своим качеством и местом.
  Несколько привязок шага дают несколько цепочек, а не одну склеенную.
  - **Обрывы** (`broken.reason`): `no_step_mapping`, `not_automated`, `handler_not_in_graph`, `no_route_handler`,
    `handler_dynamic_unresolved`, `no_runtime_mapping`, `no_port_binding`.
  - **Замечания при полной цепочке** (`issues`): `mapping_not_confirmed`, `mapping_revision_drift`,
    `no_runtime_image_identity`, `port_not_observed`.

  `confirmed` ставится только при полной цепочке без замечаний, когда все переходы `verified`.
- **Режимы §6A.1.** Трасса — `planned_process_path`, `static_path` — `static_implementation_path`.
  `observed=False` всегда. `observed_execution_path` без трассы исполнения не выдаётся: трасс в P0 нет.
- **Обратный поиск.** `impact` работает от функции, маршрута, модуля или порта. Вердикты:
  - `direct` — привязка к цели или к маршруту, который она обрабатывает;
  - `possible` — привязка к коду, из которого цель достижима вызовами;
  - `unknown` — затронутых процессов не найдено.

  Ответа «не затронуто» нет. Рядом перечисляются точки входа без привязки, динамические вызовы на пути
  и вызовы без доказанной цели. `describe` для узла без привязки отвечает `not_documented`.
- **Требования и расхождения.** `traceability` считает ссылки по видам, битые ссылки и шаги без требований
  и без привязки. `drift` показывает привязки, подтверждённые на другой ревизии кода, и пропавшие цели.
  Это сигнал на проверку, а не автоматическое утверждение.

### Реальный процесс TaskTreker

Конвейер задачи из `docs/КОНВЕЙЕР.md`: 13 шагов, 3 шлюза ворот, ручной шаг «да» владельца.

- **Пути.** Их 6: возврат анализа (был или нет) × возврат в разработку (после ревью, после QA или без
  возврата). Все 6 ведут в main только через ручной шаг «да» владельца.
- **Шаг «Идея» → `pm.py idea`.** Привязка по документу. Цепочка: команда `tools.pm:idea` → `tools.pm.cmd_idea`,
  затем обрыв `no_runtime_mapping`: CLI — не служба, и это честный разрыв.
- **Шаг «Идея» → `POST /api/work` (кнопка доски).** Привязка `inferred`, потому что документ связь кнопки
  с адресом не называет. Цепочка доходит до `do_POST` (`inline`) с замечанием `mapping_not_confirmed`.
- **Обратный поиск от `cmd_idea`** даёт `direct` шаг «Идея».
- **Привязки остальных шагов.** У ролевых шагов (анализ, разработка, ревью, QA, деплой) их нет: они идут через
  `workflow.action` по строке `op`, а такую диспетчеризацию AST не разрешает. `traceability` показывает эти
  шаги в `steps_without_mapping`.

## TT-136 (P1): вкладка «Архитектура систем» на доске

Точка входа §7A — вкладка «Архитектура систем» в верхней навигации доски (`tools/archview.js`, проекция
`tools/arch_api.py`). Данные в `dashboard.html` не встраиваются: вкладка читает их с сервера досок через
`/api/arch/*` с той же защитой, что у снимка (свой Origin, `X-TaskTreker`, токен сессии, права `arch_acl`).

| Раздел | Что показывает | Источник |
|---|---|---|
| Обзор | Свежесть и полнота снимка, состояние каждого источника, графы кода, число процессов; кнопка «Собрать» | `GET /api/arch/overview`, `POST /api/arch/scan` |
| Порты и контейнеры | Привязки портов с владельцем и проектом, поиск по порту, возможные конфликты, контейнеры | `GET /api/arch/graph` |

- **Флаг.** `network_architecture_enabled` теперь можно включить (реализация есть). Включает владелец кнопкой на
