оно не меняет ни одного файла. Rebase и cherry-pick чужой истории не делались, перенесены
только два собственных коммита этой задачи.

## 3. Найдено при аудите и исправлено сразу

**P0, FR-002: CI засчитывал отсутствие проверки как успех (TT-102).** Риск из п. 1.3 ТЗ
подтвердился в коде:

| Место | Было | Стало |
| --- | --- | --- |
| `ci.run_pipeline` | без шагов — `skipped`; ошибка запуска — `failed`; SHA только короткий | `not_configured` / `error` / `stale`, плюс полный `sha_full` |
| `deploy.run` → `pipeline_ci` | без шагов CI пропускал при ≥20 символах текста агента | текст агента в решение не входит, нужен машинный прогон |
| `pipeline.machine` `ci_test_green` | `skipped` = успех; без HEAD SHA не сверялся | `ci.green(run, head)`; не нашли HEAD — отказ |
| `orchestra.server_gate` release | `skipped` = успех, SHA не сверялся вообще | `ci.green` на текущей голове тестовой ветки |
| `ci.main` | код 0 при `skipped` | код 0 только при зелёном |

Все решения теперь принимает одна функция `ci.green(run, head)`: зелёный только `passed`,
в котором хотя бы один обязательный шаг реально прошёл, и SHA совпадает с текущим.
Старые записи `skipped` в `ci.json` читаются, но зелёными не считаются. Старые записи
с коротким SHA сверяются по префиксу. Негативная матрица — `tests/test_ci_fail_closed.py`
(17 сценариев).

**Последствие для портфеля.** У 15 из 20 проектов нет ни `ci`, ни `verify`, ни
автоопределяемых шагов. Раньше задачи этих проектов проходили CI в конвейере по тексту
агента. Теперь они остановятся на пункте CI с подсказкой задать `ci` или `verify`
в `projects.json`. По ТЗ так и должно быть (FR-002, «текстовое заверение не разрешает
release»). Включить проверки для этих проектов — решение владельца: это ручной слой.

**P0, сохранность памяти: заголовок «да» ронял индекс (TT-103).** `mdparse._q` не брал
в кавычки строки, которые при чтении становятся `bool`, `int` или `null`. Запись из Codex
с заголовком «да» читалась как `True`, `memory.build_index` падал с TypeError, а вместе
с ним падали `tt_remember` и `pm.py remember`: в память портфеля ничего не записывалось.
Исправлено в двух местах. Запись теперь берёт такие строки в кавычки. Чтение берёт
текстовые поля (`TEXT_KEYS`) как есть, поэтому уже записанные файлы читаются без правки
данных. Тесты — `tests/test_mdparse_roundtrip.py`.

**Расхождения MCP с описанием** (пока не исправлены, кандидаты в бэклог):
`tt_work op=plan` отвергает задокументированное поле `new_root` как неизвестное;
`op=update` не даёт переписать `model_plan.<ИИ>`, хотя описание инструмента это обещает.

**E1-d (TT-106; FR-014, TT3-080…083).** Свободная сессия ИИ больше не означает права начать задачу
в обход учёта: у каждой задачи есть слот от приёма до подтверждённого выпуска. Учёт один — журнал
спринта `delivery_sprints`. Правила поверх него в `tools/flow_policy.py`:
- режим `batch` — правило владельца «4 задачи до main всего состава». Действует по умолчанию;
- режим `rolling` — правило FR-014: 4 задачи на портфель, 2 на проект, выпуск освобождает ровно
  один слот, готовое к выпуску идёт раньше нового. Пока считается в shadow: каждое решение о приёме
  пишется в журнал с вердиктом второго режима, на работу не влияет;
- слот закрывается выпуском в main или операцией владельца `release_slot` с причиной.
  Раньше отменённая задача держала спринт вечно;
- внешняя блокировка (`flow_block`) видна на доске и в колокольчике, слот не освобождает;
- исключения владельца (`flow_exception`) имеют причину и срок не больше 30 дней.
  CI, ворота и права они не обходят;
- `op=flow` — снимок потока, на доске — счётчик.

Включить `rolling` — решение владельца на доске (`flow_mode`). Сначала стоит посмотреть, где shadow
разошёлся с batch: `op=flow` → `divergences`. Проверки: `test_flow_policy`, `test_flow_order`,
`test_flow_blocked`, `test_wip_race` (10 одновременных заявок на 1 слот — принята одна).

**E1B (TT-108; FR-015/016, TTU-004…010, вместе с TT-100).** Выбор ИИ для роли идёт через
`tools/provider_balance.choose`. Второго хранилища состояния провайдеров нет: канон — `provider_limits`
и запуски. `provider_modes` и `provider_decisions` — только следы.
- **Здоровье и режим.** У каждого ИИ состояние ready, degraded, rate_limited или unavailable.
  Из пары состояний складывается режим: balanced, mono_claude, mono_codex или paused_all.
  Сброс лимита без подтверждения даёт degraded, а не ready. Ready наступает после 2 успехов
  с разрывом не меньше 60 с и не раньше 180 с после сброса. Это защита от ping-pong (TC-50/51).
  Неизвестное время сброса помечается `confidence: estimated`.
- **Успех после отказа** запись не удаляет, а добавляет в `oks` (тот же успех дважды не
  считается). Подтверждённое восстановление снимает `provider_sync` — сервер вызывает его
  в каждом цикле автозапуска.
- **Доли** считаются только по принятой работе: запуск `done` с `handoff`, взвешенный уровнем
  сложности, за окна 7 и 30 дней и только в периоды balanced. Отказанная сдача, передача
  по лимиту, тимлид и периоды mono не считаются. Если событий меньше 20 или единиц меньше 30,
  статус — `insufficient_sample`, а не вывод о перекосе.
- **Выбор.** Сначала жёсткий фильтр:
  - `role_affinity.eligible`;
  - независимость проверки сложной или рисковой задачи от её автора (TTU-010);
  - исключение источника передачи;
  - здоровье;
  - в balanced — одна пробная сессия на ИИ в degraded.

  Затем порядок роли (`balance_mode=prefer`, по умолчанию) или дефицит доли с бонусом
  предпочтения роли (`balanced`). Закрепление роли владельцем мягкое: оно перекрывает баланс,
  но не лимит. Каждое решение пишется в `provider_decisions`: кандидаты, причины исключения,
  долг, доля до решения, теневой выбор второго режима, run_id. Неизвестные оценки качества
  и цены записываются как `null`.
- **Независимость проверки** — правило защиты, не функция: действует в обоих режимах. Если
  независимого ИИ нет, роль ждёт, а `orchestra.hold` не даёт автору открыть проверку своей работы.
- **Передача при лимите (TT-100, TTU-009):**
  - повтор того же события не создаёт второй запуск (TC-49);
  - живой процесс прежнего ИИ сначала коммитит незавершённое (WIP), затем закрывается — один писатель
    на рабочую копию;
  - лимит у обоих — пауза без отмены работы (TC-47).
- **Настройки владельца:**
  - `balance_mode`;
  - `target_shares` — сумма 1, допустимы 60/40 и «только один ИИ»;
  - `affinity_bonus` — 0…0.3;
  - `role_affinity`.

  Флаг `tt3_provider_balance` — отображение `balance_mode`. Снимок — `op=balance`.

Включить balanced — решение владельца. Сначала стоит посмотреть `op=balance`: где теневой выбор
расходится с текущим и хватает ли выборки. Проверки: `test_provider_balance` (16 сценариев,
в том числе синтетический корпус 60 назначений → доли в пределах 45–55%).
Не сделано в E1B: страница баланса на доске (FR-020, Dashboard 2.0). Данные доступны через `op=balance`.

**E2 (TT-109; FR-001, ТЗ §7 E2, TC-07/08, AC-49, AC-FR01).** У каждой задачи конвейера есть маршрут:
FAST, STANDARD или CRITICAL. `tools/risk_policy.py` определяет профиль риска, `tools/adaptive_pipeline.py`
собирает из него `route_plan` (схема §5.1) поверх существующих этапов. DoR и DoD не дублируются.
- **CRITICAL** — любое из:
  - риск high;
  - сложная задача (класс 3);
  - признак опасной области в тексте, scope или диффе: права доступа, оплата, секреты и криптография,
    данные и миграции, публичный API, CI и выпуск, зависимости, безопасность.
- **FAST** — только при всех условиях сразу:
  - риск low, размер S, класс 1;
  - есть scope, критерии приёмки и машинные тесты проекта;
  - дифф не больше 5 файлов и 150 строк и не выходит за scope.

  Задача только из документов получает профиль `docs_only`.
- **STANDARD** — всё остальное. Неоценённый риск и неоднозначность ведут к STANDARD, а не к FAST.
- **Повторная оценка по фактическому диффу** — перед каждым этапом после разработки. Она только поднимает
  маршрут. Поднятый маршрут закрепляется (`floor`), и текст задачи его больше не понижает.
- **Режимы (`adaptive_mode`, только владелец):**
  - `off`;
  - `shadow` (по умолчанию) — маршрут пишется в задачу и журнал, конвейер идёт полным путём;
  - `enforce`:
    - FAST пропускает «Идею» и «Анализ», но только для видов работы из `adaptive_fast_allow`
      (по умолчанию пусто). Ревью, тестирование и релиз остаются;
    - CRITICAL запрещает серверное закрытие ворот и требует независимого проверяющего;
    - дифф, вышедший за FAST, возвращает задачу на «Идею» и называет аннулированные проверки.
- **Поток.** Смена маршрута — это возврат этапа: слот задачи в потоке (FR-014) остаётся тем же.
- **Флаг** `tt3_adaptive_pipeline` — отображение `adaptive_mode` (выключен = shadow).
- **Снимки:** `op=adaptive` — сводка или маршрут одной задачи; `op=route` показывает маршрут черновика.

Эталон `tests/fixtures/routes/tasks.json` — 36 размеченных задач, по 12 на режим. Результат: точность 100%,
опасных понижений 0 (`py tools/risk_policy.py eval …`, код 1 при опасном понижении). Это синтетика:
она проверяет механизм, а не экономию. Включать FAST стоит после сравнения shadow на реальных задачах
(ТЗ §9.3: 30 задач, по 10 на режим). Проверки — `test_adaptive_pipeline` (11 сценариев, в том числе сквозной
в git: FAST пропустил анализ → дифф задел `app/auth` → возврат с CRITICAL, слот тот же).
Не сделано в E2:
- отдельный маршрут «без ИИ-ревью» для FAST: ревьюер в FAST остаётся, это осознанный запас;
- страница маршрутов на доске (FR-020).

## 4. Конфликты ТЗ с реализацией и выбранный путь

Правило владельца: брать самый эффективный путь, даже если он не самый простой.

1. **`core/*` против плоского `tools/`.** ТЗ предлагает новые пути `core/*.py` и само требует
   сверить их со структурой проекта на этапе E0 (п. 8.1). Все модули, тесты (`tests/base.py`
   перезагружает модули из `tools`), MCP и сборка дашборда живут в `tools/`. Отдельное
   дерево `core/` дало бы два места для импорта и второй набор путей в тестах.
   **Решение:** новые Python-модули кладём в `tools/` под именами из ТЗ
   (`tools/release_policy.py`, `tools/flow_policy.py`, `tools/provider_balance.py` и т. д.).
   Отдельный каталог получает только нативный код: `native/` (C++ worker) — у него своя сборка.
2. **Статусы CI.** В ТЗ `skipped` — отдельный статус, и он не зелёный. В коде отсутствие
   шагов называлось `skipped` и было зелёным. **Решение:** такое состояние называется
   `not_configured`. Статус `skipped` больше не пишется, при чтении старых записей он не зелёный.
   Необязательные шаги могут падать, но прогон, в котором прошли только они, — `not_configured`.
3. **WIP (FR-014).** Сейчас WIP есть только на этапе анализа (`wip_analysis`, А5), он считает
   сессии и этапы, а не задачи. ТЗ требует слот на задачу от приёма до подтверждённого выпуска.
   Кроме того, уже есть правило владельца: спринт из 4 задач до main всего состава (`sprints.py`).
   Через него проходят все пути приёма. По сути это тоже task-level WIP, только порционный.
   Второй учёт рядом с ним ТЗ запрещает, а молча заменить правило владельца нельзя.
   **Решение (TT-106):** одна точка приёма `sprints.admit` и один журнал `delivery_sprints`.
   В этом журнале появились слоты задач. Режим `batch` — правило владельца, действует.
   Режим `rolling` — FR-014, считается в shadow и пишет отличия. Переключает только владелец.
   Порядок диспетчера уже был «поздний этап раньше». К нему добавлен уровень «доработка после
   возврата» между ревью и разработкой.
4. **Баланс Claude/Codex (FR-015/016) и TT-100.** В `workflow.py` уже есть `provider_limits`,
   `provider_recoveries`, `failover`. В бэклоге есть TT-100 (автопередача после отказа).
   Отдельный `provider_health.py` со своим состоянием стал бы вторым источником истины
   (это запрещает TTU-004). **Решение:** каноническое состояние провайдера остаётся
   в `workflow.json`. `provider_balance.py` — чистые функции поверх него (eligibility,
   deficit, переходы balanced/mono). TT-100 закрывается внутри TTU-008/009, а не параллельно ему.
5. **Встроенный GGUF без внешнего сервера (FR-022).** `llama-server` из llama.cpp — это и есть
   внешний HTTP-сервер, ТЗ его исключает. **Решение:** собственный `tt-inference-worker` —
   дочерний процесс на закреплённом снимке исходников llama.cpp (MIT), обмен через stdio
   (JSON-lines), без порта. Ollama и HTTP — только необязательные адаптеры. До сборки
   нужен `hardware_probe` (TT3-005), потому что тулчейн CUDA на машине не подтверждён.
6. **Номера задач.** 124 микрозадачи ТЗ не заводятся в бэклог разом: по CLAUDE.md размер задачи
   влияет на прогноз, а 124 строки раздули бы его вслепую. **Решение:** задачи бэклога —
   срезы по гейтам. Коды ТЗ указываются в `refs` (TT-102: `TT3-009…013, TT3-068`),
   по ним коммиты попадают в дерево работ.
