# CLAUDE.md — регламент ведения TaskTreker

Это система проектного управления портфелем. Здесь описано, **как её обновлять**.
Читать целиком перед любым изменением данных.

## Что это

Панель по всем проектам пользователя: что сделано, готовность, затраты токенов, бэклог
с размерами, ИБ, архитектура, мощности, LLM, цели, оценка и конкуренты.
Источник истины — файлы в `data/`, дашборд собирается из них.

Система — ещё и **память работы**: знание о проектах лежит здесь, а не в контексте
ассистента. Как этим пользоваться — раздел «Оперативная память» ниже. Прочитать его
до первой команды.

## Правило номер один

**Автоматические данные не правятся руками, ручные данные не перезаписываются скриптом.**

| Файл | Кто ведёт | Что внутри |
| --- | --- | --- |
| `data/projects.json` | **Клод, вручную** | Цели, что сделано, готовность, бэклог, ИБ, архитектура, мощности, LLM, оценка |
| `data/competitors.json` | **Клод, вручную** (по результатам веб-поиска) | Конкуренты, преимущества, угрозы, вердикт |
| `data/comments.json` | **Пользователь** через `pm.py comment`, разбирает Клод | Комментарии → бэклог и техдолг |
| `data/memory/*.md` | **Клод, приём заметок, импорт авто-памяти** | Память портфеля: запросы, решения, требования, риски, итоги |
| `data/obsidian.json` | **Пользователь**, создаётся `pm.py vault init` | Путь к хранилищу, что читать и что выкладывать |
| `data/usage.json` | `collect_usage.py` | Факт по токенам и деньгам из журналов сессий |
| `data/repos.json` | `collect_repos.py` | Git, объём кода, тесты, TODO, гигиена ИБ, подозрение на секреты |
| `data/estimates.json` | `estimate.py` | Оценка оставшихся задач в токенах и деньгах |
| `data/quality.json` | `quality.py` | Индексы качества ТЗ и проработки, портфельные сигналы |
| `data/memory/index.json` | `memory.py index` | Указатель по памяти: заголовки, виды, связи, вес в токенах |
| `data/inbox.json` | `ingest.py`, разбирает Клод | Предложения задач из заметок — ждут `apply` |
| `data/tree.json` | `tree.py` | Дерево работ для дашборда |
| `data/vault_state.json` | `obsidian.py` | Что из хранилища уже разобрано — чтобы не разбирать дважды |
| `data/snapshots/*.json` | `pm.py snapshot` | История для трендов — **никогда не удалять и не править** |
| `dashboard.html` | `build_dashboard.py` | Сборка из `shell.html` + `charts.js` + `tree.js` + `app.js`. Правки тут затираются |

Единственное исключение из правила номер один: `pm.py vault pull` меняет `status`
задачи в `projects.json`, если пользователь отметил её галочкой в Obsidian. Задачи
при этом не добавляются и не удаляются — меняется только статус, и каждое изменение
печатается в отчёте. Галочку ставит человек, это такой же ввод, как `pm.py comment`.

## Оперативная память — как Клод работает с системой

Раньше знание о портфеле жило в контексте: каждая сессия перечитывала файлы данных
целиком, платила за запись кеша и за чтение кеша, а между сессиями знание терялось.
Теперь знание лежит в `data/memory/`, а в контекст попадает только указатель.

**Начало работы — одна команда:**

```bash
py tools/pm.py context
```

Она выдаёт брифинг: что требует решения, состояние проектов, верхушка бэклога и
список записей памяти — заголовки и идентификаторы, без тел. Внизу написано, во что
брифинг обошёлся и во что обошлось бы чтение `data/` целиком.

**Три правила, которые делают это работающим:**

1. **Не копировать данные системы в свою память.** Ни в `~/.claude`, ни пересказом
   в ответ. Система — и есть память; копия расходится с оригиналом через неделю.
2. **Читать точечно.** Нужна запись целиком — `pm.py recall <id>`. Нужен проект
   подробно — `pm.py status <проект>`. Не `cat data/projects.json`: это тот самый
   расход, ради устранения которого всё сделано.
3. **Узнал — запиши в систему, а не в ответ.** Решение, требование, риск, итог:

```bash
py tools/pm.py remember <проект> "заголовок" --text "суть" --kind решение
```

Виды записей: `запрос` (с чего началось), `решение`, `требование`, `риск`, `итог`,
`факт`, `источник`, `заметка`. Вид — не украшение: по нему запись попадает или
не попадает в брифинг и в дерево работ.

Авто-память самого Claude Code (`~/.claude/projects/*/memory/*.md`) система забирает
к себе: `pm.py claude-memory` (он же шаг `refresh`) делает из каждого файла запись
в проекте, где шла сессия, под корнем «Авто-память ассистента». Файлы авто-памяти
только читаются. Если ассистент всё же записал что-то туда — это не потеряется,
но правильное место для знания о проектах — `remember`.

Устаревшее не удаляется, а помечается: `pm.py forget <id> --why "почему"`. Файл
остаётся — история решений важна ровно так же, как история комментариев. Если запись
заменена новой — `--by <id преемника>`: связь сохранится в обе стороны.

### Во всех проектах: хук и MCP-сервер

`py tools/pm.py connect` подключает систему к Клоду на уровне пользователя:

- **хук начала сессии** (`tools/hook.py`) — в любом каталоге проекта портфеля сессия
  начинается с брифинга по этому проекту, в бюджете 1200 токенов; вне портфеля —
  одна строка;
- **MCP-сервер `tasktreker`** (`tools/mcp_server.py`) — инструменты `tt_context`,
  `tt_recall`, `tt_search`, `tt_remember`, `tt_forget`, `tt_status`, `tt_tree`,
  `tt_inbox`, `tt_apply`, `tt_reject`, `tt_ingest`, `tt_projects`.

В чужом проекте пользуйся инструментами `tt_*`, а не командами `pm.py`: относительные
пути там не работают. Бэклог через сервер меняет только `tt_apply`. Снять подключение —
`py tools/pm.py disconnect`, проверить — `py tools/pm.py connect --status`.

Подключать только из основного каталога системы: из временного рабочего дерева
команда откажется — после его удаления подключение сломалось бы.

### Связи и дерево

У записи есть `parent` и `root`, у задачи бэклога — поле `root` с идентификатором
записи памяти. Из этого строится дерево работ на дашборде: корневой запрос, из него
решения и требования, из него же задачи. Когда добавляешь задачу, выросшую из
запроса пользователя, **проставляй `root`** — иначе задача повиснет отдельной ветвью
и будет видно, что связь потеряна.

## Порядок обновления (выполнять именно так)

### 0. Прочитать брифинг

```bash
py tools/pm.py context
```

Дальше действовать по тому, что в нём написано, а не по памяти о прошлой сессии.

### 1. Разобрать комментарии и входящие — ПЕРВЫМ ДЕЛОМ

```bash
py tools/pm.py comments
```

Каждый комментарий со `status: "new"` — это задача, которую пользователь поставил
и ждёт в бэклоге. По каждому:

1. Понять, это бэклог, техдолг, баг или вопрос.
2. Добавить задачу в `backlog` нужного проекта в `projects.json` — с `id`, `title`,
   `size` (S/M/L/XL), `priority`, `status`, и `why` (почему это важно — своими словами,
   не цитатой комментария).
3. В `comments.json` поставить `"status": "processed"` и `"moved_to": "<проект>/<id задачи>"`.
4. **Ничего не удалять.** Разобранный комментарий остаётся в файле как след решения.

Если комментарий непонятен — не выдумывать. Оставить `new` и спросить пользователя.

Следом — входящие из заметок:

```bash
py tools/pm.py inbox
```

Это предложения, которые приём заметок нашёл сам, но в бэклог не положил: бэклог —
ручной слой, от него считается прогноз затрат по всему портфелю. По каждому решить:

- годится как есть → `py tools/pm.py apply IN-7` (задача уедет в бэклог со ссылкой
  на исходную запись памяти, связь в дереве сохранится);
- формулировка плохая → принять и **сразу переписать** `title`, `size` и `why`
  в `projects.json`: размер S/M/L/XL влияет на прогноз, а разборщик его только угадал;
- не задача → `py tools/pm.py reject IN-7 --why "почему"`. Запись остаётся в файле.

Размер и приоритет, проставленные приёмом, — догадка по словам в тексте. Проверять
их обязательно: завышенный размер раздувает прогноз по портфелю.

### 2. Пересобрать факты

```bash
py tools/pm.py refresh
```

Запускает по очереди: токены → репозитории → авто-память ассистента → индекс памяти → оценки → индексы качества →
дерево → дашборд → снимок. `--fast` пропускает сканирование репозиториев (на крупном
репозитории это минуты) — годится, когда менялись только тексты.

Если в `data/obsidian.json` включены `auto.pull_on_refresh` или `auto.push_on_refresh`,
обмен с хранилищем идёт в том же прогоне; `--no-vault` его отключает.

### 3. Сверить ручные данные с фактами

Собранные цифры часто противоречат тому, что записано в `projects.json`. **Факт побеждает.**
Что проверять каждый раз:

- **Коммиты выросли, а `done` не изменился** → прочитать `git log` за период и дописать
  сделанное. Это главный источник устаревания.
- **Появились `secrets_suspect` вне `.claude/worktrees`** → проверить глазами, это
  настоящий секрет или имя переменной. Настоящий — в `security.open_critical` и в бэклог.
- **`dirty_files` > 0 держится несколько обновлений** → незакоммиченная работа, спросить.
- **Пропал git или упало число тестов** → это регресс, вынести в тревоги.
- **Готовность** пересматривать только при доказательстве: закрытая фаза, пройденный гейт,
  новый раздел ТЗ. Не двигать проценты «на глаз» — в `readiness.basis` должно быть
  написано, на чём основана цифра.

- **Задача выполнена, а запись памяти о её запросе осталась актуальной** → дописать
  к запросу `итог` (`pm.py remember <проект> "Итог: …" --kind итог`) и связать его
  с корнем. Дерево на дашборде показывает, чем ветвь закончилась, а не только то,
  что она начиналась.

### 3а. Прочитать портфельные сигналы

`quality.json` -> `portfolio_signals`. Сигналы уровня `act` — это то, о чём надо сказать
пользователю в отчёте, даже если он не спрашивал. Они считаются из данных и не врут,
но интерпретация — твоя: сигнал называет факт, а не решение.

### 4. Обновить конкурентов — при крупном пересмотре

Не каждый раз, а когда проект заметно сдвинулся или прошло 2–3 месяца.
Веб-поиск, затем правка `competitors.json` и поля `researched`.

## Заметки и Obsidian

Входящий Markdown разбирает `ingest.py`, а не рассуждение в сессии: правила записаны
один раз и работают одинаково, рассуждение стоит токенов при каждом запуске и даёт
разный результат.

```bash
py tools/pm.py ingest путь/к/заметке.md      # файл или целый каталог
```

Что происходит: файл режется на разделы, каждый раздел получает вид (запрос, решение,
требование, риск, итог, факт), задачи-чекбоксы уходят предложениями в `inbox.json`.
Корневая запись файла становится корнем ветви, разделы — её детьми; `--root <id>`
подвешивает весь документ под существующий запрос. Проект определяется по убыванию силы
признака: аргумент `--project`, фронтматтер `project:`, **папка в хранилище** (имя,
ключ или псевдоним проекта), папка проекта вне портфеля, имя файла, тег, викиссылка
и прямое упоминание, словарь проекта. Правила, которые держат раскладку честной:

- **Папки проектов** задаются `import.project_folders` в `data/obsidian.json`
  (`Проекты/*` — каждая подпапка проект; имя без звёздочки — папка сама проект).
  Папка проекта, которого нет в портфеле, уходит в «портфель» с пометкой
  `foreign_project` — по словам такие заметки не угадываются: чужой проект похож на свои
  общими словами. Отчёт обмена называет такие папки — это вопрос пользователю, заводить ли проект.
- **Несколько проектов** в тегах или упоминаниях — заметка портфеля (профиль, обзор недели),
  если один не назван втрое чаще остальных.
- **Словарь** — последний признак: нужны два разных совпадения, впятеро больше случайного
  ожидания для такой длины заметки, и отрыв от второго проекта.
- **Разделы наследуют проект файла.** Своему признаку раздел следует, только если у него
  тег проекта или сам файл не привязан; задачи из раздела уходят в проект раздела.

Приём сам по себе:

- **вычищает ключи и пароли** до записи в память — вместо секрета пометка его вида;
  в отчёте видно, в каких заметках они лежат: оттуда их стоит убрать;
- **делит крупные разделы** — запись длиннее 1500 токенов режется по подзаголовкам
  и абзацам, ничего не теряется;
- **ведёт жизненный цикл**: раздел, исчезнувший из заметки, и все записи удалённой из
  хранилища заметки устаревают; выведенное вручную повторный приём не оживляет.

Качество раскладки измеряется, а не угадывается: `py tools/routing_eval.py <каталог>`
прогоняет размеченные заметки (поля `expect_project` и `expect_kind` во фронтматтере)
и считает точность. Встроенный набор — `tests/fixtures/routing`, порог — 85% по проекту
и 70% по виду, тест держит его и ноль заметок и разделов, ушедших в чужой проект
(заметка с разделами о разных проектах помечается `expect_mixed: true`). Если точность
падает — чинятся правила, порог не двигается. Трудный случай с реального хранилища,
на котором раскладка ошиблась, добавляется в набор — так правило не сломается снова.

Хранилище Obsidian подключается один раз:

```bash
py tools/pm.py vault init "C:/путь/к/хранилищу"
```

Дальше `pm.py vault pull` забирает изменившиеся заметки (по хешу — неизменившиеся
не разбираются заново), `pm.py vault push` выкладывает обратно портфель, страницы
проектов, дерево и записи памяти обычными заметками с викиссылками. `vault sync` —
оба действия подряд.

Что важно помнить при правках:

- Всё, что система выложила, помечено `tasktreker: generated` во фронтматтере и при
  чтении пропускается. **Метку не убирать** — иначе система начнёт разбирать
  собственный вывод и заметки размножатся.
- Каталог `export.folder` (по умолчанию `TaskTreker`) система считает своим и
  перезаписывает целиком. Своё туда не класть.
- Если пользователь жалуется, что заметка ушла не в тот проект, — смотреть не код,
  а признаки: папку заметки, `import.project_folders`, псевдонимы и словарь проекта
  (имя, цель, стек, сделанное, заголовки бэклога). Причина раскладки записана в поле
  `routing` записи памяти. Лечится строкой `project:` во фронтматтере, псевдонимом
  в `aliases` (папка в хранилище называется не так, как проект), папкой проекта
  в `import.project_folders` или более внятными `tagline` и `goal` в `projects.json`.

## Как писать в `projects.json`

- **`done`** — только то, что реально работает и проверяемо. Не «начата работа над X».
- **`readiness`** — пять цифр, и `basis` обязателен. Пустой `basis` = цифра выдумана.
- **`backlog`** — `size` влияет на оценку затрат: S=1, M=3, L=8, XL=20 коммитов
  (`size_calibration`). Ставить честно: завышенный размер раздувает прогноз по всему портфелю.
  Закрытую задачу можно оставить со статусом `done` — в остаток затрат она не входит,
  а в дереве остаётся под своим запросом. `root` — id записи-запроса, из которой задача
  выросла; `source` — откуда она пришла.
- **`aliases`** — другие имена проекта: как называется его папка в хранилище заметок,
  как его зовут в разговоре. По ним приём узнаёт проект.
- **`id_prefix`** — префикс номеров задач, если его нельзя вывести из бэклога
  (бэклог пуст, закрытые задачи убраны). Без него нумерация продолжает серию,
  найденную в бэклоге, разобранных комментариях и обосновании готовности.
- **`security`** — разделять открытое и закрытое. Закрытая находка переезжает
  в `closed_critical`, а не удаляется: история важна.
- **`assessment`** — оценка должна быть полезной, а не вежливой. Если проект стоит закрыть,
  так и писать. Пользователь просил оценку, а не одобрение.
- **Языки**: всё по-русски. Технические идентификаторы (коды требований и находок, имена
  файлов, названия веток) — как есть, не переводить.

## Чего не делать

- Не писать в `usage.json`, `repos.json`, `estimates.json`, `quality.json`, `tree.json`,
  `memory/index.json`, `vault_state.json` — затрётся.
- Не подкручивать пороги в `quality.py`, чтобы «улучшить» индекс. Пороги описывают,
  что такое хорошо; двигать их ради красивой цифры — это подделывать измерение.
  Менять их можно, только если изменилось представление о хорошем, и тогда — для всех проектов сразу.
- Не удалять снимки из `data/snapshots/` — это единственная история трендов.
- Не править `dashboard.html` — пересобирается.
- Не повышать готовность без доказательства в `basis`.
- Не выбрасывать разобранные комментарии и отклонённые предложения.
- Не удалять записи памяти — помечать `forget`, файл остаётся.
- Не перечитывать `data/*.json` целиком, когда хватает `context`, `status` и `recall`:
  это ровно тот расход контекста, ради устранения которого система и построена.
- Не копировать содержимое системы в свою память или в CLAUDE.md других проектов —
  копия устаревает молча.
- Не публиковать репозиторий без ревизии: в `data/` лежат пути, оценки, находки ИБ
  и записи памяти.

## Ветки

`разработка` → `тестирование` → `main`, движение только в эту сторону.

- **Вся работа — в `разработка`.** Прямых коммитов в `тестирование` и `main` не делать,
  туда только сливать из предыдущей ветки через `--no-ff`.
- **Перед любым слиянием — `py tools/pm.py check`.** Код возврата 1 означает «не сливать»:
  проверки ловят пустой `readiness.basis`, задачи бэклога без размера, нерасписанный
  по проектам расход токенов, расхождение бэклога с оценкой, ключи в данных и в памяти,
  записи памяти с потерянным родителем, расхождение индекса памяти с файлами, принятые
  предложения без задачи в бэклоге, несобираемый дашборд и упавшие юнит-тесты (`tests/`,
  в том числе точность раскладки заметок). Провал — это всегда настоящая проблема,
  а не придирка; чинить, а не обходить.
- Еженедельный разбор и ежедневная автозадача работают в той ветке, которая выгружена
  в рабочем дереве. Держи выгруженной `разработка`.

## Автоматизация — что уже работает само

- **Ежедневно 09:00** — задача планировщика Windows `TaskTreker\Обновление портфеля`
  запускает `ops/refresh.cmd` → `pm.py refresh`. Обновляет **только генерируемые** файлы.
  Лог: `ops/logs/refresh.log`.
- **Понедельник 10:00** — запланированная задача Клода `tasktreker-weekly-review`
  (`~/.claude/scheduled-tasks/tasktreker-weekly-review/SKILL.md`): разбор комментариев,
  сверка записанного с фактами, отчёт. Она выполняет ровно этот регламент.

Поэтому при ручном обновлении не удивляйся свежим `usage.json` и `repos.json` — их уже
обновила автозадача. Твоя работа начинается с шага 0 (брифинг) и шага 1 (комментарии
и входящие), а главная её часть — шаг 3 (сверка). Если правишь регламент ниже,
**поправь и текст запланированной задачи** — иначе еженедельный разбор будет работать
по старым правилам.

## Команды

```bash
py tools/pm.py init             # первый запуск: примеры -> рабочие файлы
py tools/pm.py context          # брифинг сессии — с этого начинать работу
py tools/pm.py refresh          # всё: токены, репозитории, память, оценки, дерево, дашборд
py tools/pm.py refresh --fast   # без пересканирования репозиториев
py tools/pm.py status           # сводка по портфелю
py tools/pm.py status <проект>  # подробно по проекту
py tools/pm.py comments         # список комментариев
py tools/pm.py comment <проект> "текст" --kind техдолг
py tools/pm.py check            # гейт перед слиянием в тестирование и main
py tools/pm.py snapshot         # снимок для трендов
py tools/pm.py open             # открыть дашборд файлом
py tools/pm.py serve            # дашборд с работающей кнопкой «Обновить данные»
py tools/pm.py connect          # хук и MCP-сервер: Клод с памятью во всех проектах
py tools/pm.py disconnect       # снять подключение
```

Память и заметки:

```bash
py tools/pm.py recall <id|слова>                    # запись целиком
py tools/pm.py remember <проект> "заголовок" --text "…" --kind решение
py tools/pm.py forget <id> --why "почему устарела" [--by <id преемника>]
py tools/pm.py claude-memory [--dry-run]           # авто-память Claude Code -> память портфеля
py tools/pm.py ingest <файл.md|каталог>             # разобрать и разложить по проектам
py tools/pm.py inbox                                # предложения задач из заметок
py tools/pm.py apply <IN-n> | reject <IN-n> --why "…"
py tools/pm.py vault init <путь> | pull | push | sync | status
py tools/pm.py tree                                 # пересобрать дерево работ
py tools/routing_eval.py tests/fixtures/routing     # точность раскладки заметок
```

## Как считаются деньги

Эквивалент по прайсу Anthropic API, а не счёт подписки: Opus 5 и Opus 4.8 — $5/$25 за 1M
(вход/выход), Sonnet 5 — $2/$10, Fable 5 — $10/$50. Запись кеша 1.25× от входа при TTL 5 минут
и 2× при 1 часе, чтение кеша 0.1× (Fable 5.1 — 0.025×). Прайс лежит в `tools/pricing.py`
и **проверяется через skill `claude-api` при каждом крупном обновлении** — он меняется.

Журнал сессий пишет каждый ответ ассистента дважды, поэтому сборщик дедуплицирует
по `requestId`. Без этого расход завышается вдвое.
